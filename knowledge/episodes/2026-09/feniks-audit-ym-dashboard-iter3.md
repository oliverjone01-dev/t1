## 3. P0-1. Правило переоткрытия отменяет само себя через один прогон

Условие переоткрытия читает поле `from` (`reports.ts:131-142`): месяц пригоден, если каждая строка несёт `from`. Но писатель того же файла ставит `from` ВСЕМ строкам, включая старые, где вклад магазинов неизвестен (`reports.ts:218`): `from: [...a.from].sort()`, а `a.from` для строк, поднятых из файла, равен `new Set(r.from || [])`, то есть пустому множеству. Запись безусловная, она выполняется в конце любого прогона, включая тот, который ничего не разобрал.

Симуляция двух последовательных прогонов на живых `data-ym/realization_monthly.ndjson` и `data-ym/realization_state.json`:

```
строк в накопленном файле = 177, из них с полем from = 0
--- ПРОГОН N ---   переоткрыто пар: 0, заблокировано: 17
--- запись прогона N ---  строк с полем from = 177, из них from == [] : 177
--- ПРОГОН N+1 ---  переоткрыто пар: 14, заблокировано: 0
  2026-02: магазинов 3, строк 43, 61 шт, 1 259 030 руб
  2026-03: магазинов 3, строк 47, 67 шт, 1 354 433 руб
  2026-04: магазинов 3, строк 43, 70 шт, 1 264 441 руб
  2026-08: магазинов 5, строк 44, 58 шт,   952 805 руб
СУММА под риском повторного наложения: 4 830 709 руб, 256 шт, 177 строк
```

Механика та же, что в итерации 2, слоем ниже: раньше «пусто в состоянии» читалось как «вклад нулевой», теперь так же читается «пустой массив в данных». Признак пригодности опирается на поле, которое писатель проставляет всем без разбора, поэтому «разбивка неизвестна» превращается в «магазин ничего не дал» после первой же записи.

Момент срабатывания важен: задвоение произойдёт именно тогда, когда фича начнёт работать. Переоткрытая пара запрашивается заново, и если Маркет отдаёт отчёт (для 2026-02/03/04 отчёты уже отдавались, эти строки оттуда), разбор складывает поверх накопленного: `a.sold += `, `a.amount += `, вычитания прошлого вклада нет. Расписание: `on: schedule` GitHub запускает только с ветки по умолчанию, значит отсчёт начинается с момента слияния в main, а не сейчас.

Три новых теста этого не видят, потому что моделируют только цикл переоткрытия и не моделируют писателя. Плюс повторён дефект итерации 2: тест объявляет собственные `attributed` и `reopen` (`reports-lib.test.ts:203-215`) вместо импорта из продового модуля. Логика в `reports.ts` не экспортируется, хотя соседний `reports-lib.ts` для этого и существует и уже импортируется тем же тестом.

## 4. Порог роста: слепая зона там, где риск

`realization_monthly.ndjson` не несёт поля кабинета или магазина (`grep -c '"business"'` = 0), поэтому `--by=business` для него не задан и задан быть не может. Повторный разбор пары сливается по SKU, число строк не меняется, остаётся только проверка суммы, а сумма растёт на долю магазина.

| Проба | Результат |
|---|---|
| весь месяц 2026-02 x2 | `FACTS INVALID ... вырос на 100%`, exit=1 |
| доля одного магазина (~19% месяца) удвоена | `строк 177 -> 177, месяцев 4 -> 4, аномалий нет`, exit=0 |
| пара `1023124/2026-03` в netting x2 (16.7% месяца) | поймано на ключе пары, exit=1 |

То есть на netting новый ключ `--by=business` действительно закрыл разбавление вторым кабинетом (это в плюс автору), а на реализации порог остался разбавленным долей магазина. Ровно тот файл, где живёт механизм задвоения, защищён слабее всех.

## 5. Два запланированных ложных срабатывания

**5.1 sku_views на смене месяца.** Файл не накопительный, пока отчёт отдаёт агрегат за окно: `shows()` выбрасывает прежний агрегат окна и кладёт новый (`reports.ts:376`). В живом файле одна дата на кабинет (4504 строки, `aggregate: true`). Первый прогон нового месяца переносит агрегат на дату нового месяца, и прошлый месяц исчезает целиком:

```
$ npx tsx validate-facts.ts /tmp/fx/sku_views_oct.ndjson data-ym/sku_views.ndjson --month-key=date --sum=views --by=business
FACTS INVALID: 74986385/2026-09: строк было 3916, стало 0 (потеря)
                1023124/2026-09: строк было 588, стало 0 (потеря)     exit=1
```

**5.2 Реализация на легальном доборе УПД.** По состоянию: 2026-08 - 7 магазинов продавали, 1 дал строки, 6 ждут выпуска УПД. Сейчас 2026-08 самый свежий месяц файла и потому исключён из потолка. Как только появится строка за 2026-09, месяц станет закрытым, и приход шести отчётов даст рост много больше 25%. Для реализации «закрытый месяц вырос» - штатный сценарий, а не аномалия; порог роста в текущем виде спорит с самой фичей добора.

Обе ситуации приводят к красному ночному прогону без реального дефекта данных. Отключить гейт при этом можно легально: `YM_FACTS_GROW_GATE=20` проходит валидацию (диапазон (0, 20]) и разрешает рост 2000%, проба на месяце x2 даёт exit=0. Валидация env закрыла случайное отключение, но оставила намеренное.
