# Контракт данных Kostya-AI

## Откуда берётся снимок

`analytics-mvp/rop/data/rop.json` в ветке **`rop-dashboard-v1`** (не в `main`). Собирается `analytics-mvp/src/scripts/b24/fetch-rop.ts` ежедневно через `.github/workflows/b24-snapshots.yml`, cron `20 2 * * *` UTC.

Сеть к `glassmemory.bitrix24.ru` из песочницы Claude Code заблокирована (403). Живой запрос к Bitrix возможен только внутри GitHub Actions. В сессии снимок берётся так:

```bash
git fetch origin rop-dashboard-v1
git show origin/rop-dashboard-v1:analytics-mvp/rop/data/rop.json > /tmp/rop.json
```

Размер на 2026-08-07: 20 МБ, 22 969 сделок, 12 772 лида. Не читать файл целиком через Read, только через скрипты.

## Поля сделки, которые использует Kostya-AI

| Поле | Тип | Используется в | Надёжность |
|---|---|---|---|
| `id` | строка | все детекторы, ссылка в Bitrix | надёжно |
| `title` | строка | вывод, прокси-группировка D12 | надёжно, но формат «4127Сделка #4127 Наталья» требует нормализации |
| `mgr` | строка | агрегация по менеджеру | надёжно |
| `stage`, `stageCode` | строка | лимиты стадий | надёжно |
| `won`, `lost` | bool | фильтр открытых | надёжно |
| `budget` | число | D07, приоритет флагов | надёжно, 114 открытых сделок с нулём |
| `created` | дата | контекст | надёжно |
| `activity` | дата | **D02 ТИШИНА** | надёжно, основной сигнал |
| `taskDue`, `taskSubj` | дата, строка | D03 | надёжно, ближайшее открытое дело |
| `tasksOpen` | число | D04 | надёжно |
| `closed` | дата | окно D06 | надёжно |
| `reason` | строка | D06 | надёжно |

| `tasksNoContact` | число | **не используется** | производное от `lastTouch`, наследует недостоверность |

## Три известных источника вранья

**1. `lastTouch` и `touch90` недостоверны.**

На снимке 2026-08-07: 496 из 650 открытых сделок имеют `touch90 = 0`, то есть якобы ни одного касания за 90 дней. При этом 228 из них имели активность (`activity`) в пределах последних 7 дней.

Причина в атрибуции: `channelMix` в `fetch-rop.ts` считает касанием только звонок, письмо или сообщение открытой линии, привязанное к сделке, её контакту, компании или лиду-источнику. Общение через каналы, которые не интегрированы с Bitrix, и активности с другой привязкой в счётчик не попадают.

**Правило:** никогда не выносить обвинение «менеджер не касался клиента» на основании `lastTouch`. Тишина считается по `activity` (LAST_ACTIVITY_TIME). Поле `tasksNoContact` («просроченное дело, после которого не было касания») наследует ту же ошибку и тоже не используется, хотя по смыслу это лучший из возможных детекторов имитации работы.

**2. Полей из ТЗ Кости в Bitrix24 не существует.**

Нет «Даты решения клиента», нет «Даты следующего контакта», нет стадий «Счёт отправлен» и «Связаться позже». Детекторы D05 и D13 работают на прокси или спят. Каждый прокси-флаг несёт в `evidence.proxy` пояснение, дайджест обязан его показывать.

**3. Группировка по клиенту невозможна.**

`fetch-rop.ts` не выбирает `CONTACT_ID` и `COMPANY_ID` в выходную структуру, хотя запрашивает их у Bitrix (они используются внутри для атрибуции касаний). Поэтому «сделка-свалка», ключевая проблема у 6 из 8 менеджеров у Кости, детектируется только прокси по нормализованному названию.

**Как починить, одна строка:** добавить `contactId` и `companyId` в объект сделки в `fetch-rop.ts` (данные уже есть в `dealRowById`). После этого D12 переводится с эвристики на факт, и появляется возможность считать конверсию по клиенту.

## Что ещё стоит добавить в снимок

По убыванию пользы для Kostya-AI:

1. `contactId`, `companyId` (см. выше). Стоимость: одна строка, данные уже в памяти скрипта.
2. Горизонт всех открытых дел по сделке, а не только ближайшего. `tasks.dues` внутри `fetch-rop.ts` уже собирается, но в выход попадает только количество. Нужно для антигейминга «дело на три месяца вперёд».
3. Автор последней активности (менеджер или клиент). Сейчас неизвестно, кто последним написал. Разница принципиальная: «менеджер молчит 20 дней» и «клиент не отвечает 20 дней после трёх касаний» это разные диагнозы и разные действия.

Пункт 3 самый ценный и самый дорогой: требует разбора `DIRECTION` активностей на уровне сделки.

## Слой B: тексты сообщений (не реализовано)

Половина находок Кости (T01-T09 в `defect-catalog.md`) про содержание переписки: пустые письма, отсутствие имени, размытые сроки, жаргон, орфография, защита вместо извинения. В `rop.json` тел сообщений нет.

**Спецификация сборщика:**

| Что тянуть | Метод Bitrix24 | Поля |
|---|---|---|
| Тела активностей | `crm.activity.list` | `ID`, `OWNER_TYPE_ID`, `OWNER_ID`, `TYPE_ID`, `PROVIDER_ID`, `DIRECTION`, `SUBJECT`, `DESCRIPTION`, `CREATED`, `AUTHOR_ID` |
| Комментарии таймлайна | `crm.timeline.comment.list` | `ID`, `ENTITY_ID`, `ENTITY_TYPE`, `COMMENT`, `CREATED`, `AUTHOR_ID` |

**Объём.** Активностей по сделкам за 365 дней в текущем снимке десятки тысяч. Тянуть тела всех бессмысленно и дорого. Разумный срез: только исходящие (`DIRECTION = 2`) по открытым сделкам за последние 30 дней. Это сотни, а не десятки тысяч.

**Приватность.** Тела переписки с клиентами это персональные данные. Не коммитить сырые тексты в репозиторий. Сборщик должен отдавать только детекторные признаки (есть ли приветствие, есть ли имя, найдены ли размытые формулировки, число орфографических аномалий) плюс короткий цитируемый фрагмент для доказательства, не весь текст. Это требование к реализации, не пожелание.

**Детекторы слоя B, которые работают на регулярках без модели:**

| Код | Регулярка или признак |
|---|---|
| T01 ПУСТОЕ_ПИСЬМО | есть вложение, длина текста после удаления подписи меньше 20 символов |
| T02 БЕЗ_ИМЕНИ | нет имени контакта в первых 100 символах |
| T03 РАЗМЫТЫЙ_СРОК | `ближайш\|в скором\|постара\|как только\|на сколько возможно\|как будет готов\|думаю после` |
| T04 ЖАРГОН | `закрут\|забылся\|запар\|замотал` |
| T07 ОРФОГРАФИЯ | ` ,` , ` \?`, `[.!?][А-Яа-я]` (нет пробела после знака) |
| T09 ШТАМП | `длительное ожидание\|судьб\w+ рассмотрения` |

T05, T06, T08 требуют понимания контекста, их отдавать модели, а не регулярке.

## Проверка снимка перед разбором

Скрипт `kostya-audit.mjs` делает это сам, но при ручном разборе проверять то же:

1. `generated_at` свежее 36 часов, иначе флаг D14 и явная оговорка в отчёте.
2. `counts.deals` в разумном диапазоне. Резкое падение означает сбой коннектора, а не чистку воронки.
3. Дата разбора берётся из `generated_at`, а не из системного «сегодня». Прогон вчерашнего снимка сегодняшней датой нарисует лишний день просрочки на каждой сделке.
