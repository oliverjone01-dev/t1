# Перенос дашбордов на свой сервер (VPS)

Цель: все дашборды, сборы данных и расписания работают на нашем сервере. Код, история и
правки остаются в git: Claude работает как сейчас (ветка, PR, merge), а сервер сам забирает
изменения и выкатывает их. Функционал сохраняется, переезд идёт по одному дашборду, без
общего «дня X».

Состав контура: [`bootstrap.sh`](bootstrap.sh) (подготовка сервера), [`bin/`](bin) (команды),
[`conf/`](conf) (ветки, задачи, шаблон секретов), [`jobs/`](jobs) (задачи по расписанию),
[`site/`](site) (сборка сайта), [`systemd/`](systemd), [`nginx/`](nginx),
[`test/smoke-local.sh`](test/smoke-local.sh) (проверка без сервера), [`INVENTORY.md`](INVENTORY.md)
(что и в каком порядке переносим).

## 1. Как будет устроено

```
  Иван ──задача──> Claude (web / desktop)
                      │  ветка → PR → проверки CI → merge
                      ▼
              GitHub (приватный)  ◄── только КОД и ИСТОРИЯ
                      ▲
                      │ git fetch каждые 2 мин (ключ только на чтение)
  ┌───────────────── VPS (Россия) ──────────────────────────────────────┐
  │ gg-poll ─► gg-release <ветка>   неизменяемый релиз кода ветки         │
  │                 │  пути данных = ссылки на /srv/gg/data               │
  │ systemd-таймеры ─► gg-job <задача>   Bitrix / OZON / Яндекс API       │
  │                 │  успех: коммит в git данных (локальный) → gg-site   │
  │ gg-site ─► www/releases/<время> ─► www/current (атомарно, откат)      │
  │ nginx + HTTPS + личные логины ─► https://<домен>/rop/ ...             │
  │ /etc/gg/secrets.env (ключи API)   restic ─► S3 (бэкап данных и ключей)│
  └──────────────────────────────────────────────────────────────────────┘
```

Принципы:

- **GitHub хранит только код и историю.** Данные клиентов в GitHub больше не уходят: они живут на
  сервере, версионируются локальным git данных (`/srv/gg/data`, `git log` по каждому снимку) и
  шифрованным бэкапом в S3.
- **Сервер сам забирает код.** В GitHub нет ключей от сервера, входящих подключений из GitHub нет.
  Ключ сервера к GitHub - deploy key только на чтение.
- **Релизы неизменяемые.** Каждый коммит ветки = отдельная папка; переключение ссылкой за одну
  операцию; откат одной командой. Хранятся 3 релиза каждой ветки и 5 сборок сайта.
- **Один писатель у данных.** Задача пишет данные либо в GitHub, либо на сервере, не в обоих местах.
- **Сбой не роняет сайт.** Упала задача - её недописанные данные откатываются, сайт не трогается,
  приходит алерт. Упал шаг сборки сайта - раздел берётся из прошлой сборки, а не исчезает.
  Пропущенный из-за перезагрузки запуск выполняется сразу после старта (в GitHub такие терялись).
- **Переезд по одному дашборду.** Чего ещё нет на сервере, nginx отдаёт с GitHub Pages через себя:
  один адрес работает с первого дня (раздел «переходный режим» в `nginx/gg.conf.template`).

Что меняется для людей: новый адрес (свой домен), вход по личному логину и паролю вместо общего
хэш-пароля, данные обновляются по расписанию без пропусков, страница `/status/` показывает
свежесть каждого источника.

## 2. Как работать через Claude

Каждый день:

1. Иван ставит задачу Claude. Claude правит код в ветке, открывает PR.
2. CI проверяет: `analytics-tests` и `infra-check` (shellcheck и полный прогон
   `test/smoke-local.sh`, если PR трогает `infra/vps`).
3. Merge → через 2 минуты сервер выкатывает ветку и пересобирает сайт. На `/status/` видно,
   какой коммит сейчас работает.
4. Не понравилось → revert PR в GitHub (история сохраняется, сервер откатится сам).

Правила:

- **На сервере руками код не правим никогда.** Любая правка - через git. Ручная правка пропадёт при
  следующем выкате и не попадёт в историю.
- **Секреты - только в `/etc/gg/secrets.env`**, в git лежит шаблон с именами (`conf/secrets.env.example`).
- **Числа в дашбордах проверяются по CLAUDE.md §15** и после переезда: сверка с эталоном, три типа
  периода, отчёт о покрытии.
- **Диагностика.** Облачной сессии Claude сервер не нужен: код и тест контура работают без него.
  Если нужно посмотреть логи или перезапустить задачу, Claude Code на компьютере Ивана (Desktop или
  CLI) ходит на сервер по SSH и выполняет `gg-status`, `gg-job <имя>`, `journalctl -u gg-job@<имя>`.
  Выводы и исправления всё равно идут через PR.

Команды на сервере (от пользователя `gg`):

| Команда | Что делает |
|---|---|
| `gg-status` | релизы веток, последняя сборка сайта, итоги задач, таймеры, диск |
| `gg-job --list` / `gg-job <имя>` | список задач / запустить задачу сейчас |
| `gg-poll` | подтянуть GitHub и выкатить сейчас, не дожидаясь таймера |
| `gg-release <ветка> [sha]` | выкатить ветку (с `sha` - откатить на конкретный коммит) |
| `gg-site` / `gg-site --rollback` / `gg-site --list` | пересобрать сайт / вернуть прошлую сборку / список |
| `git -C /srv/gg/data log` | история данных: какая задача когда что изменила |

## 3. Сервер

- **Локация: Россия (Москва или Санкт-Петербург).** Это данные клиентов (152-ФЗ, требование
  хранить базу в РФ). Кроме того, API Bitrix24, OZON и Яндекса отвечают быстрее.
- **Размер для старта: 4 vCPU, 8 ГБ RAM, 100 ГБ NVMe, Ubuntu 24.04.** Это ориентир, а не замер:
  `dialog.json` около 93 МБ парсится целиком в память Node, зеркало репозитория около 700 МБ,
  данные с историей растут, сборка сайта идёт параллельно с задачами. Через месяц смотрим
  `gg-status` (диск) и нагрузку и меняем тариф.
- **Timeweb Cloud подходит**: VPS + Object Storage (S3) для бэкапов + поддомен (например
  `dash.genglass.ru`, A-запись на IP сервера).
- **Внешний мониторинг** `https://<домен>/healthz` (отвечает без пароля и без данных) любым
  сервисом проверки доступности.

## 4. План по фазам

### Фаза 0. Безопасность (день 1)
Раздел 0: закрыть репозиторий, юридическая оценка, остановить выгрузки контактов в git.

### Фаза 1. Сервер и контур (дни 2-3)
1. Заказать VPS и поддомен. A-запись поддомена направить на IP.
2. На сервере от root: `DOMAIN=dash.<домен> LE_EMAIL=<почта> bash bootstrap.sh`. Первый запуск
   покажет deploy-ключ: добавить его в GitHub (Settings → Deploy keys, **без** права записи) и
   запустить скрипт второй раз.
3. Пока этот PR не влит в main, контур берётся из ветки PR: `OPS_BRANCH=<ветка> bash bootstrap.sh`
   (после merge поменять `GG_OPS_BRANCH` в `/etc/gg/gg.env` на `main`).
4. Логины: `htpasswd -B /etc/nginx/gg.htpasswd <логин>`, у каждого человека свой.
5. Бот для алертов (BotFather) и чат: `GG_ALERT_BOT_TOKEN`, `GG_ALERT_CHAT_ID` в `/etc/gg/secrets.env`.
6. S3-бакет и `RESTIC_*` в secrets → `systemctl enable --now gg-backup.timer`.

**Готово, когда:** `https://<домен>/` открывается под паролем, все разделы видны (пока через
прокси с GitHub Pages), `/status/` работает, пробный алерт дошёл в Telegram.

### Фаза 2. Пилот РОП + Офис, параллельный прогон (неделя 1)
1. Заполнить `B24_WEBHOOK_URL` (рекомендация: новый входящий вебхук в Bitrix24 с минимальными
   правами, отдельный для сервера, чтобы его можно было отозвать независимо от GitHub).
2. `gg-poll`, затем `gg-job rop-snapshot`, затем `/usr/local/sbin/gg-apply-timers` (включить расписание).
3. **Параллельный прогон 3-5 дней.** GitHub продолжает работать как сейчас, сервер снимает свои
   данные. Каждый день сравнить `/rop/` на сервере и на github.io: число сделок и лидов, продажи,
   выручка текущего месяца (§15: закрытый месяц, часть месяца, текущий месяц).
4. **Готово, когда:** 3 суток по 8 снимков без пропусков, числа совпадают или расхождение
   объяснено (снимки сняты в разное время), алерт при искусственном сбое приходит.

### Фаза 3. Переключение по волнам (недели 2-5)
Порядок и состав - в [INVENTORY.md](INVENTORY.md). Каждая волна = несколько PR по чек-листу
раздела 5. Волна 1 (РОП ГГ целиком) переключается только вместе с Telegram-ботом и личными
дашбордами менеджеров: они читают тот же `rop.json`. После переключения волны в том же PR
убирается cron из старых воркфлоу и шаг из `deploy-pages.yml`: данные этой волны перестают
публиковаться на github.io.

### Фаза 4. Закрытие GitHub Pages (после последней волны)
1. Удалить `deploy-pages.yml`, выключить Pages, убрать блок `@legacy` из nginx.
2. Заменить абсолютные ссылки `oliverjone01-dev.github.io/t1/...` на относительные (6 файлов),
   убрать `sub_filter`.
3. Удалить из GitHub Secrets ключи, которые больше не нужны (оставить только для CI и ИИ-задач, §7).
4. Решить про историю git: вычистить снимки и выгрузки (`git filter-repo`, после предупреждения
   всех, у кого есть клоны) - репозиторий станет в разы меньше и чище.

### Фаза 5. Эксплуатация (постоянно)
- Ежемесячно: `sudo gg-backup --check` и пробное восстановление одного файла из бэкапа.
- Ежеквартально: ревизия логинов в `gg.htpasswd` (ушедшие сотрудники).
- Обновления безопасности ОС ставятся сами (unattended-upgrades); раз в полгода - плановая
  перезагрузка в нерабочее время.

## 5. Чек-лист переноса одной задачи и дашборда (шаблон PR для Claude)

1. Найти в [INVENTORY.md](INVENTORY.md) задачу, шаг сайта и всех, кто читает её данные.
2. `conf/branches.conf`: пути данных ветки = то, что задача делает `git add` в воркфлоу.
3. `jobs/<имя>.sh`: перенести `run:`-шаги воркфлоу. Убрать checkout, setup-node, `npm ci` (это
   делает релиз), `git commit`/`git push` и dispatch деплоя (это делает `gg-job`). Секреты - те же имена.
   Если воркфлоу берёт данные из другой ветки - `gg_src <ветка>`.
4. `conf/jobs.conf`: строка с расписанием, время в UTC как в старом cron.
5. `site/steps/NN-<раздел>.sh`: перенести шаг `deploy-pages.yml`. `git fetch` + `git worktree add`
   заменить на `gg_src <ветка>`, `$GITHUB_WORKSPACE/_site` - на `$SITE`, в шапке `# sections: ...`.
6. `bash infra/vps/test/smoke-local.sh` зелёный (новую ветку добавить в тест).
7. После merge на сервере: `gg-job <имя>` руками, сверка чисел по §15, параллельный прогон.
8. Отдельным PR после сверки: убрать cron из старого воркфлоу и шаг из `deploy-pages.yml`.

## 6. Секреты

Значения из GitHub Secrets прочитать нельзя (так устроен GitHub). Для сервера ключи берутся из
первоисточника или перевыпускаются: Bitrix24 - новый входящий вебхук; OZON Seller и Performance -
новые ключи в кабинете; Яндекс Директ, Метрика, Маркет - новые OAuth-токены; Точка - новое
приложение или refresh token; Telegram-боты - `/token` у BotFather. Перевыпуск полезен и сам по
себе: у сервера свои ключи, которые отзываются, не трогая GitHub. Полный список имён -
`conf/secrets.env.example`. Передавать значения только на сервер (SSH), не в мессенджерах.

## 7. ИИ-задачи: ограничение Anthropic

Anthropic не обслуживает запросы с российских IP-адресов. Поэтому на сервере в РФ не будут
работать ни Claude Code, ни задачи, которые ходят в API Claude: `ai-rop-nightly`, `sales-audit`,
ИИ-разбор диалогов.

Рекомендация: **эти задачи остаются в GitHub Actions** (там API доступен). Сейчас они читают
`rop.json` и `dialog.json` из git. После переключения волн 1-2 этих данных в git не будет, поэтому
сервер будет отдавать им **обезличенные факты** (без телефонов, email и текстов клиентов) по
отдельному адресу с токеном. Как именно, решается в PR волны 1. Альтернатива: небольшой второй
сервер в зарубежной локации только для ИИ-задач с теми же обезличенными фактами.
Решение за Иваном до переключения волны 1.

Это же ограничение значит, что Claude работает с кодом в облаке (как сейчас) или на компьютере
Ивана, а не на самом сервере. Контуру это не мешает: сервер получает всё через git.

## 8. Превью веток (после волны 1)

Сейчас превью - отдельные шаги `deploy-pages.yml` с ручным выбором ветки (`/preview/`,
`/rop-preview/`, `/direct-preview/`). План для сервера: ветки `claude/*` с открытым PR

пилота, когда понятно, какие дашборды чаще правятся.

## 9. Проверено до выката

- `bash infra/vps/test/smoke-local.sh`: полный цикл на копии репозитория (выкат веток, сайт,
  задача с коммитом данных, падение задачи с откатом, откат сайта, новый коммит кода при
  сохранении данных сервера, генерация таймеров, отказ на плохое имя задачи, перенос раздела
  из прошлой сборки при падении шага).
- Настоящий `build-rop.ts` в серверном релизе (node_modules из кэша, данные через ссылки):
  результат совпал с запечённым в git HTML (отличается только штамп времени сборки).
- shellcheck по всем скриптам без предупреждений.

Не проверено (нужен настоящий сервер): `bootstrap.sh` целиком, nginx и сертификат, systemd-таймеры,
`fetch-rop.ts` с настоящим вебхуком, бэкап в S3. Это первые шаги фаз 1-2.
