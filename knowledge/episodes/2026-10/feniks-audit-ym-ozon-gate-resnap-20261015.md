## Ответы на пять вопросов автора

### 1. Ослабляет ли фикс гейт

Нет. Доказательство двумя путями.

**Статика.**
- Между слепком (yml:86) и пересъёмом (yml:145) пишут только `ym:orders` и `ym:catalog` (yml:115, 118).
- Оба пишут только через `yp()` = `${YM_DIR}/...` (common.ts:13). YM_DIR = `process.env.YM_DATA_DIR || "data-ym"` (common.ts:7).
- Импортируемые ими модули (env.ts, connector/ym-partner.ts, derive-lib.ts) в файлы не пишут.
- YM_DATA_DIR не задан ни в одном воркфлоу: grep по .github = 0.
- Шаг «Базовый слепок» пишет только в /tmp/ym-base.

**Динамика** (харнесс, обе ревизии):
- Правка tracked OZON-файла до reset: гейт молчит и до, и после фикса (readme_race+own_before_tracked: PASS / PASS). Причина: reset --hard её стирает, на remote остаётся x1.
- Новый файл до reset: PASS / PASS. Список md5 новых файлов не содержит, поэтому до фикса такой файл тоже невидим.
- Без гонки (push сразу, reset нет) правку из окна ym:orders ловят обе версии: norace+own_before_tracked FAIL / FAIL.

**Вывод.** В пути с reset фикс сужает окно гейта: было [yml:86..266], стало [yml:145..266]. Но в отрезанном куске в OZON никто не пишет. То, что могло бы попасть в tracked-файлы, стирает reset в обеих версиях. Поведение меняется ровно в одном месте: пропадает ложное падение на чужом коммите.

### 2. Цикл retry 1..5

Корректно. Пересъём стоит после каждого reset, поэтому слепок всегда снят с дерева последнего reset.
- **retry2:** чужой коммит перед push #1 и второй перед push #2. push / fetch / reset = 3 / 2 / 2. После фикса PASS, на remote оба чужих коммита и наш data-ym. До фикса FAIL.
- **fetchfail:** fetch #1 падает. Дальше continue без reset: дерево не меняется, слепок остаётся согласованным. fetch #2 проходит, итого 3 / 2 / 1, PASS.
- **retry2 + своя правка public/index.html после цикла:** FAIL в обеих версиях.

### 3. `set -uo pipefail` без -e

Посылка неверна: -e в шаге есть.
- GitHub запускает `shell: bash` как `bash --noprofile --norc -eo pipefail {0}`, а `set -uo pipefail` флаг -e не снимает.
- В репо это уже записано живым инцидентом: rop-tg-bot.yml:56-61, «по умолчанию GitHub запускает шаг как `bash -eo pipefail`».
- Локально под той же строкой вызова `$-` = `ehuB`. `( cd /нет && ... )` роняет скрипт с кодом 1, а `{ ...; }` - нет.

Что это значит для фикса:
- Ошибку пересъёма ничто не глушит, она валит шаг сразу. `|| true` закрывает только ветку data, ровно как в yml:91.
- Но шаг падает ДО push. Сценарий resnap_fail: в свежем main нет public/*.html.
  - После фикса шаг промежуточного коммита выходит с exit 1, на remote data-ym = y1. Заказы и каталог дня не сохранены.
  - До фикса в том же сценарии push y2 прошёл, упал только гейт.
  - Это G3.
- Макет автора идёт без -e (`#!/usr/bin/env bash` + `set -uo pipefail`, строки 1-3), поэтому этот режим не моделирует. Под ним тот же сценарий проходит шаг и падает на гейте с сообщением «no properly formatted checksum lines».

### 4. Пути в md5-файле

Совпадают байт-в-байт.
- Сценарий pathequiv: чужой коммит только в README, затем reset и пересъём. `public.md5` и `data.md5` после пересъёма совпали со снятыми шагом yml:86 (filecmp, оба файла).
- Гейт (yml:266, рабочая папка analytics-mvp) проверяет пути вида `public/x.html` и `data/x.json`. В race он проходит, в race+own_after_* падает ровно на изменённом файле.

### 5. Другие точки, где дерево OZON меняется до гейта

Нет.
- Git-операции в yml, которые меняют дерево:
  - checkout (yml:80) - до слепка;
  - reset (yml:138) - теперь с пересъёмом;
  - reset (yml:298) - после гейта.
- Рабочие скрипты analytics-mvp git не вызывают: `child_process` есть только в 10 файлах *.test.ts.
- Чужой коммит, пришедший после успешного push промежуточного шага, дерево не меняет: до гейта fetch нет (late_foreign PASS / PASS).
