## 3. Решения и почему
- Все решения v18-v25 в силе.
- Схема 1С по Маркету (установлено по цифрам): ДБС-магазины проводятся «Отчётом комиссионера» по отчёту Маркета о реализации (месяц Маркета, нетто = доставлено − возвраты; август №73 взят gross), ФБС-магазин FBS OOO проводится реализациями «Яндекс маркет фбс» по «доставлено» gross; все 52 реализации относятся к Маркету, 23 «без договора» тоже (в выгрузке 19.10 у них другие контрагенты, в 20.10 все «Яндекс маркет фбс»).
- Пара документу 1С ищется сначала по отчёту Маркета о реализации (файл кабинета или API), потом по выгрузке заказов по месяцу сбора; иначе ложные «магазины без документа» (ошибка 19-20.10, см. реестр E0xx).
- Сверка «сошлось» только между семьями: банк 1С / документы 1С / реестр API / файл кабинета. Файл кабинета = API до копейки (FBS OOO май-июль).
- Добор отчётов через плановый сборщик по слову Ивана «добирай» 20.10: только чтение, кабинет не меняется, данные в main как у ежедневного прогона.

## 6. Грабли
- Все грабли v22-v25 §6 в силе.
- `git reset --hard`, `git merge --ff-only` после пересоздания ветки классификатор не даёт: `git branch -m` старой + `git checkout -b <ветка> origin/<ветка>`.
- xls 1С: `pip install xlrd`. Файлы кабинета Маркета openpyxl читает с UserWarning, подавлять `2>/dev/null`.
- Отчёт об исполнении поручения считает «получено» по дате оплаты; отчёт о реализации и 1С - по доставке в месяце Маркета; выгрузка заказов дашборда - по дате сбора за продажу. Три разных месяца у одного заказа, сравнивать только одноимённые базы.
- Лимит Маркета: 1 отчёт в 2 мин на кабинет, прогон собирает 5-10 пар и останавливается; пары «pending» добираются следующим прогоном без rebuild.
- Отчёт о реализации по API за февраль-апрель до 20.10 был без магазина (from=[]) - после rebuild с магазином.
