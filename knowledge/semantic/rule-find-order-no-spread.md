# Правило: расход ищется по номеру заказа, а не раскладывается

**Решение Ивана, 28.09.2026.** Действует для всех таблиц «Денег» (OZON и Маркет) и для любых будущих источников расходов по заказу (ведомость доставки, реклама «за заказ», услуги партнёров, возвраты).

## Правило

1. Расход по заказу ищется **по номеру этого заказа** и встаёт на **его дату заказа** (аналитика «Денег» по заказам построена по дате заказа).
2. Если номер записан не так, как в выгрузке площадки, его приводят к номеру площадки: «бывш.» (действует номер до «бывш.»), номер без хвоста отправления, два номера в одной строке. Сумма одной строки делится только между отправлениями, которые эта строка сама назвала (по штукам).
3. Если заказ по номеру **не нашёлся**, расход **не раскладывается** ни по другим заказам, ни по артикулу, ни по месяцу, и не добирается строкой «Общие расходы». Он выводится **плашкой над таблицей** со списком номеров и сумм, по образцу плашки «Нет производственной СС»: пробел должен быть виден, а не спрятан в чужих строках.
4. Остаток «итог документа за окно минус разнесённое» как источник числа запрещён, если документ и таблица стоят на разных датах (отгрузка против заказа, начисление против заказа).

## Почему

22.09 в таблицу по заказам добавили добор: ведомость по артикулу (на дате отгрузки) минус разнесённое по номерам (на дате заказа) раскладывалась по заказам артикула. Доставка заказа 79214675-0180-2 (оформлен 31.07, отгружен 04.08, 3 666 ₽) стояла в июле по номеру и второй раз попадала в август добором: у 46952822-0108-1 выходило 3 559 ₽ при 2 948 ₽ в ведомости (замечание Ивана 28.09). Тот же механизм сидел в строке «Общие расходы».

## Как исполняется

- Код: `analytics-mvp/src/scripts/delivery-match.ts` (`matchLedger`), подключён в `build-katya.ts`.
- Тесты: `delivery-match.test.ts`. В их числе инвариант на живых данных: «найдено + не найдено = вся ведомость до копейки», и точная сверка заказа 46952822-0108-1.
- Плашка: `#ordan-dlwarn` над «Аналитикой по заказам».
- Счёт перевозчика по отменённому заказу стоит на этом отменённом заказе (товар возили, покупатель отказался), а не пропадает.

## Какая дата у «Нашей доставки» в какой таблице (Иван 28.09, вариант Б)

- Таблицы «по дате заказа» («Аналитика по заказам», «по артикулам (по дате заказа)»): строка ведомости стоит на своём заказе по номеру, на дате заказа.
- Таблица «Аналитика по артикулам (за выбранный период)» (базис начислений), водопад и план-факт: строка ведомости стоит на своём заказе по номеру, на **дате начисления этого заказа OZON** (Иван 28.09, пересмотр варианта Б): расход в один день с выручкой заказа. Заказ, который OZON ещё не начислил (в пути, отменённый с расходом перевозчика), - на дате фактической доставки из ведомости, без неё - на дате отгрузки; суммы таких названы плашкой.
- Блок «Логистика по городам»: ведомость по дате **отгрузки** (Иван: «логистику оставь как есть»). За месяц суммы с таблицами различаются, за всё время - только на строки без найденного заказа.
- Инвариант (тест): ряд по дате начисления = всё, что нашлось по номерам; найдено + не найдено = вся ведомость.

## Статус «ОТМЕНЕН» в ведомости (Иван 28.09)

Строка ведомости со статусом «ОТМЕНЕН» в расход не идёт вовсе, ни по дате заказа, ни по дате отгрузки. «Вернули на склад», «Возврат» и прочие статусы с оплаченной отправкой остаются расходом. Текущий месяц берётся из ведомости тем, что в ней есть (раньше отбрасывался целиком); где ведомость кончается, говорит плашка.

## Чтение сумм ведомости (ФЕНИКС 29.09, п.1; решение Ивана 29.09)

- Сумма читается при любом написании: неразрывные пробелы, переносы строк, «1871х2» (= 1871 × 2). Несколько сумм в одной ячейке - несколько отправок одного заказа, складываются. Непонятный текст - ошибка сборки с номером строки, **не 0** (`tools/delivery/ledger_money.py`).
- Сдвиг столбцов: в «Стоимости отправки» FALSE, а число в «Стоимости доставки» - это наш расход; доход покупателя по такой строке неизвестен. Строки перечислены плашкой `#ordan-dlissues` (Иван поправит ведомость, правило остаётся страховкой).
- Строка без суммы (FALSE без сдвига) - не ноль молча, а заказ в плашке «в ведомости нет суммы».
- Сверка с сырым файлом: `tools/delivery/check_ledger_raw.py` (в vitest): сумма файла данных = сумма ведомости до рубля, ни одна непустая ячейка не прочитана как 0.

## Выгрузка ведомости 29.09 (лист 2)

- Берётся только лист 2 (полная перевыгрузка; март-август по «Стоимости отправки» совпали с прежней до рубля). Лист 1 в сырьё не кладётся: сборщики читают все листы, и суммы бы задвоились.
- Суммы со знаком «₽» и через плюс («3647+3132») читаются; TRUE в «Стоимости отправки» при сумме в соседнем столбце - тот же сдвиг, что FALSE.
- Вторая таблица листа 2 (с строки 1877, 118 строк OZON): Иван 29.09 убрал её шапку и поменял местами суммы в 163 строках, так что наш расход теперь в «Стоимости отправки», как в первой таблице. 12 строк, повторяющих первую таблицу, совпадают с ней и схлопываются. Страховка осталась: если посреди листа снова встретится шапка, сборщики на ней останавливаются (`ledger_money.second_header`) и называют её плашкой `#ordan-dlissues`.
- Даты во второй таблице: в её бывшей шапке не было «Даты доставки (крайней)», поэтому фактическая дата стоит на месте крайней, а «Дата доставки факт.» пуста. Для не начисленных OZON заказов этой таблицы расход встаёт на дату отгрузки.
