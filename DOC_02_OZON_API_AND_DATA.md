# DOC_02 - OZON API, словарь данных и провенанс

Версия: 1.0 - Июнь 2026

Этот документ - источник правды по тому, откуда берётся каждая цифра, какие у OZON API подводные камни и как трактовать метрики. Секреты (Client-Id, ключи) намеренно НЕ приводятся в этом файле - они в нодах n8n и должны переехать в секрет-хранилище (см. ТЗ).

## 1. Два API OZON

### 1.1 Seller API
- Хост: `api-seller.ozon.ru`
- Авторизация: заголовки `Client-Id` и `Api-Key`.
- Аккаунт GENGLASS: Client-Id `3971004` (с финансовыми данными). Есть второй аккаунт GEN GROUP.

### 1.2 Performance API (реклама)
- Хост: **`api-performance.ozon.ru`** - это критично.
- **Подводный камень:** `performance.ozon.ru` (без `api-`) мёртв - отдаёт 307 и уводит в редирект-петлю. Использовать только `api-performance.ozon.ru`.
- Авторизация: OAuth client_credentials. `POST /api/client/token` с `{client_id, client_secret, grant_type:"client_credentials"}` -> `{access_token, expires_in:1800}`. Дальше `Authorization: Bearer <token>`.

## 2. Эндпоинты Seller API (используемые)

### 2.1 Аналитика - `POST /v1/analytics/data`
Тело: `{date_from, date_to, metrics, dimension, limit, sort}`.

Порядок метрик, который мы используем (важен, ответ - массив в том же порядке):
```
["revenue","ordered_units","hits_view","hits_tocart","delivered_units","returns","cancellations"]
```
Измерения:
- `dimension:["day"]` - суммарные строки по дням (агрегируем сами).
- `dimension:["sku"]` - строка на SKU: `row.dimensions[0] = {id, name}` (полное имя товара) + `row.metrics` в том же порядке.

### 2.2 Остатки - `POST /v4/product/info/stocks`
Тело: `{filter:{visibility:"ALL"}, limit:1000, last_id}`. Ответ: `items[{offer_id, stocks:[{sku, present, reserved}]}]`, `result.last_id` для пагинации.
Используется для: карты `sku -> offer_id` и остатка `present - reserved`.

### 2.3 Цены и индекс цен - `POST /v5/product/info/prices`
Тело: `{filter:{visibility:"ALL"}, limit:1000, cursor}`. Ответ: `items[{offer_id, price_indexes:{external_index_data:{price_index_value, min_price}, color_index}}]`, `cursor` для пагинации.

**Индекс цен пригоден и используется:**
- `price_indexes.external_index_data.price_index_value` - число (например 0.90, 1.19).
- `price_indexes.color_index` - `SUPER` / `GREEN` / `RED` / `WITHOUT_INDEX`.
- Трактовка: значение меньше 1 = мы дешевле рынка (хорошо, SUPER/GREEN); больше 1 = дороже рынка (RED, карточка проседает по цене).
- Покрытие: около 184 из 187 SKU имеют индекс. `[ДАННЫЕ]`

### 2.4 Финансы - `POST /v3/finance/transaction/*`
`/totals` и `/list` использовались в finance_cockpit для разнесения P&L. Это основа сверенного слоя. Внимание: возможен двойной счёт "Базовое вознаграждение" против агентского акта - требует аккуратности при разнесении.

## 3. Performance API (реклама)

### 3.1 Кампании - `GET /api/client/campaign`
Ответ: `{list:[{id, title, state, advObjectType}]}` (порядка 110 кампаний).

### 3.2 Статистика - `GET /api/client/statistics/daily/json?campaignIds=...&dateFrom=...&dateTo=...`
- Батч: не более 25 `campaignIds` за запрос. Тянем объединённый диапазон один раз, режем по строковой дате в коде.
- Строка: `id, title (= offer_id для SKU-кампаний), date (YYYY-MM-DD), views, clicks, moneySpent, orders, ordersMoney`.
- **Подводный камень:** `moneySpent` и `ordersMoney` приходят с запятой как десятичный разделитель ("0,00"). Парсить через замену запятой на точку.

## 4. Критичные подводные камни (собраны в одном месте)

1. **Хост рекламы** - только `api-performance.ozon.ru`.
2. **Десятичная запятая** в рекламных суммах.
3. **Пол данных - февраль 2026.** Январь 2026 и декабрь 2025 = нули (аккаунт начал работу в феврале). Любой запрос клампится снизу к `2026-02-01`, сверху к вчера.
4. **Таксономии не совпадают.** Реклама именована по offer-id (GGT/GGM...), аналитика - по русским названиям товара. Поэтому ДРР по линиям из рекламы ненадёжен: большая часть рекламного расхода ложится в "прочее". **Достоверен только суммарный ДРР канала.** В интерфейсе ДРР по линиям подаётся как ориентир, не как факт.
5. **VIOLUR на маркетплейсе** - нарушение позиционирования (перегородки не должны быть на МП). Система помечает появление линии VIOLUR как нарушение.

## 5. Словарь метрик

| Метрика | Определение | Источник | Слой |
|---|---|---|---|
| Оборот / GMV | `revenue` из analytics/data, сумма по периоду | Seller analytics | оперативный |
| Заказано штук | `ordered_units` | Seller analytics | оперативный |
| Показы | `hits_view` | Seller analytics | оперативный |
| В корзину | `hits_tocart` | Seller analytics | оперативный |
| Доставлено | `delivered_units` | Seller analytics | оперативный |
| Возвраты | `returns` | Seller analytics | оперативный |
| Отмены | `cancellations` | Seller analytics | оперативный |
| Конверсия показ-корзина | `hits_tocart / hits_view` | расчёт | оперативный |
| Конверсия показ-заказ | `ordered_units / hits_view` | расчёт | оперативный |
| Средний чек (AOV) | `revenue / ordered_units` на SKU | расчёт | оперативный |
| Возврат % | `returns / (ordered_units + returns)` | расчёт | оперативный |
| Расход на рекламу | сумма `moneySpent` | Performance | оперативный |
| Выручка с рекламы | сумма `ordersMoney` | Performance | оперативный |
| ДРР (доля рекламы в выручке) | `расход / выручка с рекламы`, суммарно | Performance | оперативный (только суммарный достоверен) |
| Индекс цены | `external_index_data.price_index_value` + `color_index` | Seller prices | оперативный |
| Склад | `present - reserved` по offer_id | Seller stocks | оперативный |
| OOS (склад 0 при продажах) | `units > 0 и stock <= 0` | расчёт | оперативный |
| Чистая прибыль | разнесено по Актам сверки | финансы OZON, подписанные Акты | сверенный (только закрытые месяцы) |
| Реализация | выручка после базовой комиссии | финансы OZON | сверенный |
| Маржа | `чистая прибыль / реализация` | расчёт | сверенный |

## 6. Провенанс и правило Protocol 9

Каждая цифра в интерфейсе и в ответах агента должна нести метку:
- `[ДАННЫЕ]` - получено из OZON API или из подписанных Актов сверки.
- `[ГИПОТЕЗА]` - расчёт-предположение; рядом обязательно явное допущение и, для крупных эффектов, downside.

Чистая прибыль за незакрытый период (май-июнь и далее, пока не подписан Акт) **не вычисляется и не показывается**. Это защита от ложного чувства точности.
