## 1. Цель

Маркетинговый дашборд на данных Roistat: визит → заявка → сделка → выручка в разрезе
рекламного канала. Этого нет ни в Директе, ни в Метрике по отдельности. Критерий «готово»
по разделу 15 регламента (`knowledge/os/analytics-dod.md`): каждый показатель сверен с
внешней правдой, проверен на трёх типах периода, покрытие показано в дашборде.

Разведка API, первый живой срез и **построчная раскладка сверки закончены**. Витрина не
начата: ждёт ответа Ивана по виджетам (раздел 7).

## 3. Решения и почему

Из v1-v3, менять не надо: разведка до загрузчика; всё, что ходит в Ройстат, живёт в GitHub
Actions (из контейнера `cloud.roistat.com` закрыт прокси, ключ в секретах); баланс Директа
из API Директа; агрегаты из `analytics/data`; период полуоткрытый, `to` = первый день
следующего периода, сутки по UTC; выручка НЕ из `custom_16..26` (пустые); слова «прибыль» в
витрине нет; продажа = класс статуса `paid` по карте Ройстата; `potential_revenue` по строкам
не суммируется.

Новое, по итогам раскладки 30.09:

- **Деньги по сделке брать со строки лида, когда строки сделки нет.** 62 сделки из 113 лежат
  у Ройстата только строкой лида со ссылкой `order_id_alias`. Искать деньги на строке сделки -
  значит записать их в нули и объявить пропажу 5.2 млн, которой нет.
- **`payment_revenue` по месяцам брать из `analytics/data` как есть.** Поля даты, по которому
  Ройстат раскладывает её по месяцам, в `order/list` нет. Построчная сверка доказывает
  полноту и суммы, но не месячную нарезку.
- **Полнота обхода меряется числом СТРОК одного прохода против `total`**, а не числом
  различных id: `total` считает строки. Расхождение строк и различных id - это дубли,
  отдельный вывод; дубли от съехавшего окна различает повтор обхода.
- **Поле денег не выбирается «по наибольшей сумме».** Эталон не воспроизведён - берётся
  штатное `revenue`, цифры помечаются гипотезой.
- **Запрет по имени поля сильнее белого списка**, и поверх него запрет по порядку величины.

## 6. Грабли

- **Стенд должен врать так же, как врёт API.** Четыре дефекта живой прогон нашёл только
  потому, что заглушка отдавала форму проще настоящей (скалярный `status` вместо объекта,
  нет `custom_fields`, значение разреза вместо заголовка).
- **Добавил повторы - добавь случай, где повторы не спасают.** Иначе прежний отрицательный
  случай начинает проходить, и проверка перестаёт проверять (так fail-closed стал fail-open).
- `node --check` не ловит удалённое имя. Перед push гонять стенд.
- У каждой текстовой замены проверять, что цель найдена (`assert old in s`).
- Логи Actions читаются с хвоста, итоговая таблица печатается последней.
- Контейнер клонирует репозиторий **shallow**: `git merge` с origin-веткой говорит
  «refusing to merge unrelated histories». Лечится `git fetch --unshallow origin`, не reset.
  Unshallow идёт дольше 120 секунд - пускать в фоне.
- **Номера в реестре сталкиваются.** `E056` был занят в main другой ошибкой; моя переехала
  на `E073`. Перед записью проверять `origin/main`, а не только свою ветку.
- Конфликт с main по `knowledge/errors/registry.jsonl` и `traces/` - обычное дело, решается
  объединением сторон. Реестр сливать по id, а не маркерами.
- Петля трейс-хуков починена в main. После мержа main лишних коммитов «traces: автозапись
  хука» нет - проверено. Нюанс: `97ec4151` от 14:54 сделан через три часа после фикса и не
  является его потомком, то есть какая-то сессия писала трейсы, не втянув main.
