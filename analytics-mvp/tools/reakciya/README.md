# Вкладка «Реакция»: откуда берутся данные

Остальные семь вкладок собираются из снимков `data/*.ndjson`, которые тянет ночной синк
`ozon-snapshots.yml`. У «Реакции» источник другой, и автоматизировать его нельзя.

Ей нужны: лог действий по рекламным кампаниям, история ставки оплаты за заказ по обоим
инструментам, предельные цены и акции по всем товарам, воронка по товарам. Кабинет отдаёт
это только под живой сессией продавца по кукам. Ни GitHub Actions, ни сервер туда не
достучатся, поэтому срез снимается вручную из активной вкладки Chrome.

## Цикл обновления

1. Снять кабинет по `КАБИНЕТ_эндпоинты.md`, положить выгрузки в `tools/reakciya/data-cabinet/`.
2. **Сверить имена файлов с началом `build.py`** (см. ниже «Ловушка с датами в именах») - иначе шаг 3 пересчитает старый срез, и `data_until` не сдвинется.
3. `python3 tools/reakciya/build.py` - пересчёт в `data/reakciya.json` (нужны python3, pandas, numpy).
4. `npm run reakciya` - сборка `public/katya-reakciya.html`. Или `npm run katya`, он теперь собирает и её.
5. `npm run smoke` - прогон контролов.
6. **Доставить в репо** (обязательный шаг, см. ниже). Без него срез остаётся на маке, а дашборд стоит на прежней дате.

Шаг 1 требует человека с доступом в кабинет. Шаги 2-6 воспроизводимы.

## Доставка в репо (ОБЯЗАТЕЛЬНО - иначе снятие бесполезно)

«Собрал на маке» и «дашборд обновился» - это два разных состояния. Между ними один шаг, и он часто
пропускается: срез надо закоммитить и запушить. Пока этого нет, Иван на вкладке видит старую дату.

После шагов 3-5 из активной ветки (по умолчанию `claude/focused-davinci-tKJCt`):

```
cd analytics-mvp
git add data/reakciya.json public/katya-reakciya.html public/katya-reakciya-lite.html katya/reakciya/
git commit -m "data(reakciya): срез кабинета ГГГГ-ММ-ДД (data_until ГГГГ-ММ-ДД)"
git push origin claude/focused-davinci-tKJCt
```

Проверка, что доехало (должна показать свежую дату, не 09.09):

```
git show origin/claude/focused-davinci-tKJCt:analytics-mvp/data/reakciya.json | grep -o '"data_until":"[^"]*"'
```

Сырьё из `data-cabinet/` в git не кладём (см. ниже) - в коммит идёт только агрегат `data/reakciya.json`
и собранные страницы. Если снятие прошло, а `data_until` в репо не сдвинулся - значит забыли этот шаг
либо сработала ловушка с датами в именах.

## Ловушка с датами в именах файлов

Имена входных выгрузок зашиты в первых строках `build.py` с конкретными датами, например:
`snapshot_514_2026-09-09.psv`, `analytics_sku_daily_2026-06-12_09-09.psv`,
`ads_campaign_history_2026-06-13_09-10.psv`. Скрипт читает ровно эти имена. Если положить свежий срез
под новыми именами, а константы не обновить - `build.py` молча пересчитает **старые** файлы за 09.09,
и `data_until` останется прежним (симптом: снятие было, а дата на дашборде не двигается).

Два варианта, любой рабочий:
- переименовать свежие выгрузки в те же имена, что зашиты в `build.py` (быстро, но теряется дата в имени), **или**
- обновить константы с именами в начале `build.py` под новые файлы (правильнее - имена честно несут дату среза).

После пересчёта `build.py` печатает диапазон данных (`аналитика SKU-дней: ... до ГГГГ-ММ-ДД`) -
свериться, что верхняя дата = дате свежего снятия, а не 09.09.

## Почему сырые выгрузки не в git

`tools/reakciya/data-cabinet/` весит около 7 МБ и содержит аналитику по каждому SKU по дням.
Репозиторий публичный, GitHub Pages раздаёт всё, что в нём лежит. Срез `data/reakciya.json`
(133 КБ) уже агрегирован и попадает на страницу, которая и так публична, поэтому его храним,
а сырьё - нет. Если сырьё понадобится для пересчёта, его приносит тот, кто снимал кабинет.

## Что должно быть в data-cabinet

| файл | что внутри |
|---|---|
| `snapshot_514_ГГГГ-ММ-ДД.psv` | снимок цен и акций по всем товарам |
| `analytics_sku_daily_*.psv` | воронка по товарам по дням |
| `price_history.pkl` | история цен по товарам |
| `ads_campaign_history_*.psv` | лог действий по кампаниям |
| `cpo_history.psv` | история ставки оплаты за заказ, все товары |

Плюс в `data/`: `events_new.psv` (свежие события рекламы) и `cur_prices.psv` (текущие цены).
Точные имена файлов зашиты в начале `build.py`.
