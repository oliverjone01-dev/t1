## 1. Цель

Маркетинговый дашборд на данных Roistat: путь визит → заявка → сделка → выручка и
прибыль в разрезе рекламного канала. Это то, чего нет ни в Директе, ни в Метрике по
отдельности. Критерий «готово» по разделу 15 регламента (`knowledge/os/analytics-dod.md`):
каждый показатель сверен с внешней правдой, проверен на трёх типах периода, покрытие
SKU и оборота показано в самом дашборде.

Доступ к API зафиксирован и проверен живыми запросами. Постраничный обход разведан.
Дашборд не начат. **Разведка изменила конструкцию**: ось времени и выручку по каналам
нельзя строить на `order/list`, см. раздел 4.

## 3. Решения и почему

- **Разведка до загрузчика.** Набор методов зависит от тарифа и прав ключа; писать синк
  под метод, которого нет, значит отлаживать вслепую.
- **Всё, что ходит в Ройстат, живёт в GitHub Actions.** Из контейнера Claude
  `cloud.roistat.com` и `help-ru.roistat.com` закрыты egress-прокси, а ключ лежит в
  секретах и прочитать его модель не может. Это не обойти открытием сети.
- **Агрегаты берём из `analytics/data`, не из сырых списков.** Сначала потому, что списки
  игнорируют период. После разведки 30.09 причина стала сильнее: канал лежит на лиде,
  деньги на сделке, и склейка у себя воспроизводит атрибуцию Ройстата с ошибками.
  Выручка по каналам - метрики `custom_16..26` в разрезе `marker_level_1`.
- **Ось времени не берём из `order/list.creation_date`**: поле бывает штампом импорта.
- **Покрытие показываем на витрине, а не в комментарии.** Доля лидов и доля денег,
  привязанных к каналу, считаются отдельно - усреднять их в одну цифру нельзя.
- **Баланс Директа берётся из API Директа, не из Ройстата.** Разделение ролей: Ройстат
  считает списанное, остаток живёт в кабинете.
- **В логи не уходят значения клиентских полей.** Только имена ключей, размеры массивов,
  итоги. Ключ вырезается на случай эха в тексте ошибки.

## 6. Грабли

- **Логи Actions читаются только с хвоста** (`get_job_logs` отдаёт `tail_lines`), поэтому
  итоговая таблица в разведчиках печатается последней. Не переставлять обратно.
- Скачать zip логов нельзя: `results-receiver.actions.githubusercontent.com` закрыт прокси.
- `workflow_dispatch` регистрируется по main. Новый воркфлоу в рабочей ветке не виден в
  Actions, пока не влит; запускать можно с `ref` рабочей ветки, но файл должен быть в main.
- Первый прогон `analytics/data` упал на `visitsCount` - имя придумано по памяти. Имена
  метрик брать только из справочника.
- `visit/list` заголовком `Api-key` ответил `request_limit_error`: у API есть лимит,
  ночной синк делать с паузами и повтором.
- Шаблон поиска `счет|счёт` ловит «Расчёт» - ложные совпадения возможны.
- **Список статуса прогона в Actions отдаётся с задержкой:** `list_workflow_jobs` держал
  `in_progress` минут десять после того, как прогон на деле закончился за 97 секунд.
  Смотреть по `completed_at` шага, а не ждать смены статуса.
- **Деление пополам требует монотонности.** Первый вердикт «привязка обрывается
  2026-03-05» был неверен дважды: край рваный, а дата - штамп импорта. В скрипте теперь
  явная проверка окон правее границы и запрет выводить дату.
- Обход растущей базы по `offset` задваивает записи: складывать по ключу `id`, снимать
  `total` до и после (E056).

Вопросы к пользователю (без ответа работа встанет на первом же виджете):

1. **Добавлять ли баланс Директа в ночной синк** (`AccountManagement.get`, только чтение,
   мутаций кабинета нет). Правки синка рекламного кабинета идут с его слова.
   Варианты: а) добавить (рекомендую, один запрос, закрывает «сколько осталось денег»);
   б) не трогать, баланс смотреть в кабинете.
2. **Какие четыре виджета в первую очередь.** Варианты:
   а) канал → визиты → лиды → сделки → выручка, помесячно (рекомендую: это то, чего
      нет ни в Директе, ни в Метрике);
   б) ДРР и стоимость лида по каналам;
   в) воронка по стадиям Б24 в разрезе канала;
   г) покрытие: какая доля лидов и какая доля денег вообще привязана к каналу.
   Пункт «г» нужен в любом наборе - без него цифры а-в выглядят полными, не будучи ими.

Закрыто разведкой 30.09 (было пунктами 3-6):

- Постраничный обход: `offset`, в записях. Страница не менее 20 000.
- Период: применяет `analytics/data`, списки игнорируют.
- Лимит запросов: простого «N в минуту» нет, зависит от тяжести метода. Нужны пауза и
  повтор с растущим ожиданием - это не зависит от точного числа.
- Доля заявок с привязкой к визиту: измерена и оказалась не той величиной, за которую
  её принимали. Раскладка в разделе 4.

Осталось техническим долгом, на конструкцию не влияет:

- Формат `period` для `statistics/get-daily`. Метод не нужен, пока `analytics/data`
  отдаёт агрегаты за период.
- Точный потолок `limit` (проверено до 20 000, усечения не было).
- Что делать с записями, чьи статусы отсутствуют в справочнике (29-30 из 500).
