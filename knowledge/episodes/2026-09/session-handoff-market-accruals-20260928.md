## 3. Технические факты и грабли

- **`analytics-mvp/src/scripts/build-katya.ts` - ОДИН билдер на OZON и Маркет** (ветвление
  `IS_OZON`). Это главное место столкновения с параллельной сессией по OZON.
- **`npm run ym:build` пишет только в `public/market/`.** Общий `npm run build` перезапишет и
  страницы OZON - не запускать.
- **Два базиса на Маркете, их нельзя смешивать:**
  - по дате заказа (`svod_orders.json`): доставлено минус отмены и возвраты. Блоки «Аналитика по
    заказам» и «Аналитика по артикулам (по дате заказа)»;
  - по дате проводки (`pnl_sku_daily.ndjson` из `united-netting`): блок «за выбранный период».
- **Отсечку отрицательного АДМ нельзя делать по артикулу или по заказу.** Это разные разрезы
  одних и тех же строк, замер 23.09 дал расхождение 45 605 ₽ между двумя сводами. Единственный
  общий атом - строка свода, поле `admBase` копится на ней и суммируется вверх.
- **Платёж покупателя берётся из `orders.ndjson`** (`p_buyer` × нетто-штуки), а не из
  `netting.ndjson`: в неттинге статьи «Платёж покупателя» нет за февраль-апрель, а готовые
  `paid_by_type` расходятся со сводом на 822 542 ₽ на возвращённых позициях. Сверка базы налога
  с `paid_by_type.PAYMENT` по 16 парам (кабинет, месяц) дала **дельту 0 ₽**, 30 818 087 ₽.
- **УПД (`realization_monthly.ndjson`) покрывает период частично** (300 строк, 7.8 млн ₽: декабрь
  2025 и февраль-август 2026). Причина не в расчёте: Маркет упирается в лимит генерации отчётов,
  часть магазинов остаётся в `pending` (`realization_state.json.by_month`).
- **Страница «Товары» расходится со сводом** (июль ~52 200 ₽): не берёт нашу доставку по
  отменённым и не отсекает отрицательный АДМ. **Решение Кати 23.09: не трогать.**

## 4. Проверка перед мержем (Definition of Done, CLAUDE.md §15)

```bash
cd analytics-mvp
npx vitest run src/scripts/ym/<нужный>.test.ts   # точечно, полный прогон один раз перед мержем
npm test                                          # 736 тестов на момент хендоффа
npm run ym:build && npm run smoke                 # 22 страницы
```

Числа считаются готовыми только после сверки с внешней правдой (отчёт о реализации, P&L канала,
лист СС), проверки трёх типов периода (закрытый месяц, часть месяца, текущий месяц) и отчёта о
покрытии.

## 5. Как не столкнуться с сессией по OZON

1. Перед каждым мержем подтянуть `origin/main` в ветку.
2. Из этой ветки **OZON не трогать** (Катя правит его отдельно).
3. Конфликты в `traces/*/agents.jsonl` решать объединением строк с дедупликацией и проверкой
   JSON, а не выбором стороны.
4. Никогда не запускать общий билд, только `ym:build`.

## 7. Гигиена сессий (договорённость 28.09)

Одна сессия = одна задача = один PR. Закрывать сессию сразу после мержа, при смене темы или при
появлении компакции контекста. Фоновые проверки PR не заводить: каждое пробуждение перезагружает
системный контекст и стоит дороже самой проверки. Перед закрытием говорить «закрываем, сделай
хендофф» и получать такой файл; новую сессию открывать фразой «читай <путь к хендоффу> и
продолжай с пункта N».
