# Управление доступом к дашбордам

Блок на главной странице использует `/_access/api/`. Nginx проверяет общий Basic Auth и передаёт подтверждённый `$remote_user` сервису через Unix-сокет. Присланный клиентом заголовок личности заменяется. Сервис не слушает TCP-порт.

Первичная установка от root после выпуска ветки:

```sh
python3 /srv/gg/src/claude__friendly-brahmagupta-me4gk0/current/infra/vps/access/install.py
```

Установка переносит существующие хеши в `/srv/gg/access/users.htpasswd`, сохраняя `/etc/nginx/gg.htpasswd` как стабильную ссылку. Существующие пароли не меняются. При первой установке администратором становится имеющийся `yanchoglov`. Пользователь `genglass` остаётся обычным входом. Domglass использует свой файл и не изменяется.

`gg-access-api.service` работает от отдельного пользователя `gg-access`, имеет право записи только в свой каталог данных и runtime-каталог. Изменения пользователей выполняются через интерфейс: ручная замена файла паролей может нарушить его владельца и права. Резервные копии установки находятся в `/srv/gg/backups/access-ui-*`.

Мутации требуют административной роли, одноимённого Origin, JSON и CSRF-токена. Удаление собственного входа, снятие с себя административной роли и удаление последнего администратора запрещены. Старые пароли и хеши через API не возвращаются. Журнал сервиса содержит действие и имена пользователей, без паролей.

После обновления исходников повторный запуск установки переключает код сервиса и перезапускает его, сохраняя пользователей и роли. После перезапуска открытые административные страницы следует обновить для получения нового CSRF-токена.

Проверка API на временных данных: `python3 test_server.py`. Тест не использует рабочий файл доступа, API моделей или Telegram.
