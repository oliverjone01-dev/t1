## Step 12.5 - итерация 1 (2026-07-08)

ФЕНИКС: **7.6/10, verdict: return**. Ключевой gap: HITL-гейт мутаций был только промпт-правилом, без технического enforcement (Protocol 6 требует governance через permissions).

Доработки по rework-ТЗ (все выполнены):
1. `yd-api.sh` - read-only на уровне кода (только метод `get`, остальное exit 3);
2. Новый `yd-api-write.sh` - мутации только при approval-файле `.claude/approvals/direct-write.ok` с сегодняшней датой (создаётся после явного апрува Ивана, действует один день, в `.gitignore`); каждый вызов логируется в `traces/YYYY-MM-DD/direct-writes.jsonl` (P14);
3. Hook `direct-write-gate.sh` (PreToolUse Bash) - второй эшелон: блокирует CLI-мутации и сырой curl с мутирующими методами (включая экранированные кавычки), read-вызовы пропускает; зарегистрирован в `settings.json`;
4. Read-скрипты внесены в allow-лист `settings.json` (снижение alert fatigue, gap #2);
5. Hard Rule в timur.md: никаких мутаций и бюджет-рекомендаций до закрытия P0 атрибуции (gap #6);
6. WB/Ozon Ads исключены из обоснования роли (gap #4), CR уточнена до 37/39 = 94.9% с источником (gap #5), standing-роль обоснована конкретной нагрузкой + sunset clause (gap #3);
7. Строка ростера в CLAUDE.md не вносилась до повторного аудита (rework-ТЗ #6).

Тесты гейта: 14/14 PASS (read проходит; мутация через read-обёртку exit 3; write-обёртка без апрува exit 3; hook блокирует CLI-мутацию, write-вызов и сырой curl-мутацию, пропускает read/cp; с approval-файлом сегодняшней даты пропускает).

Остаточный риск (зафиксирован честно): hook сопоставляет строку команды - обходится через shell-переменные (`M=susp""end`). Компенсация: первичный контроль не hook, а сами обёртки (read-only код + approval-файл внутри `yd-api-write.sh`), их через переменные не обойти.

## Step 12.5 - итерация 2 (2026-07-08)

ФЕНИКС: **7.9/10, verdict: return**. Live-атака вскрыла главный дефект: авторизация-по-существованию-файла подделываема самим агентом.

- [ДАННЫЕ] ATTACK A: ФЕНИКС сам создал `.claude/approvals/direct-write.ok` (строка «approved-by: ivan (SELF-FORGED)») - `yd-api-write.sh` пропустил гейт и реально отправил `campaigns add` на api.direct.yandex.com. Отказ пришёл только со стороны Яндекса (error_code 8000). P14-трейс атаку зафиксировал (traces/2026-07-08/direct-writes.jsonl).
- [ГИПОТЕЗА] Причина отказа 8000 не установлена: мусорные params дают 8000 независимо от прав токена. Считать токен write-ограниченным нельзя.
- [ДАННЫЕ] ATTACK B: создание approval-файла через `echo >` и через Write tool не перехватывалось ничем.

Доработки по rework-ТЗ итерации 2 (все выполнены):
1. Новый hook `approvals-guard.sh` (PreToolUse: Bash И Write|Edit) - блокирует любое обращение к `.claude/approvals/**` и `.claude/state/**` через инструменты агента. Approval-файл теперь может появиться только рукой человека вне Claude Code;
2. Hard Rule #2 enforced в коде: `yd-api-write.sh` блокирует мутации при существовании флага `.claude/state/p0-attribution.open` (создан, закоммичен) - даже с валидным апрувом. Снятие флага - человеком по решению Ивана (GitHub UI / локальный терминал);
3. Scope апрува сужен: approval-файл обязан содержать явный whitelist `methods: add,update`; wildcard не поддерживается; метод вне списка - блок. Дневной blanket на «все мутации» невозможен;
4. Закрыт вектор, не замеченный аудитом: env-override `YD_APPROVAL_FILE` удалён из обёртки (позволял подставить `/tmp/fake`), путь захардкожен;
5. Приоритет остаточных рисков переставлен (см. ниже).

Тесты итерации 2: 15/15 PASS (guard блокирует Write/Bash в approvals и state, включая ATTACK B; P0-флаг блокирует мутацию с валидным апрувом; method-whitelist enforced; approval без methods и вчерашний approval - блок; env-подмена игнорируется; read-путь жив).

Остаточные риски (приоритет исправлен по gap #5):
1. **Главный:** внутри одного sandbox абсолютная неподделываемость недостижима - хуки видят строку команды, а не семантику; теоретический обход: агент пишет скрипт-файл, который создаёт approval изнутри. Компенсации: guard закрывает все прямые пути (Write/Edit/Bash), каждый write-вызов оставляет P14-след до исполнения, финальный контроль - scope OAuth-токена на стороне Яндекса (вне досягаемости агента).
2. Вторичный: обход `direct-write-gate.sh` shell-переменными - парируется тем, что первичный контроль в обёртках.
