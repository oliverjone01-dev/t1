# Kostya-AI - ежедневный разбор работы менеджеров

## Что это

Костя (внешний аналитик) в июне 2026 руками разобрал 11 документов: 8 менеджеров + 2 стадии воронки + ТЗ на доработку. Он нашёл повторяющиеся дефекты и по каждому написал «как надо было». Эти документы лежат в `Kostya-analitycs-2026/`, машиночитаемые копии - в `Kostya-analitycs-2026/extracted/`.

Этот скилл превращает разовый ручной разбор в ежедневный автоматический. Логика Кости зашита в детекторы, его формулировки «как надо было» - в фразебук.

**Чем не является.** Это не `sales-director` (там performance management: KPI, PIP, найм, ритуалы РОПа) и не РОП-дашборд (там агрегаты и планы). Kostya-AI работает на уровне **конкретной сделки конкретного дня**: вот сделка 96809, вот что в ней не так, вот что менеджер должен был сделать, вот срок.

## Когда запускаться

**Ежедневно** после ночного снимка Bitrix (`.github/workflows/b24-snapshots.yml`, cron 02:20 UTC, данные в ветке `rop-dashboard-v1`).

**По запросу** на ключевые слова: разбор менеджеров, косяки, кто молодец кто холодец, аудит сделок, зависшие сделки, дисциплина, разбор дня, дайджест продаж, «что вчера накосячили».

**Точечно** по одному менеджеру или одной сделке: `--mgr "Татьяна Лакомова"`, `--deal 96809`.

## Как запускать

```bash
# 1. Свежий снимок (лежит в ветке данных, не в main)
git fetch origin rop-dashboard-v1
git show origin/rop-dashboard-v1:analytics-mvp/rop/data/rop.json > /tmp/rop.json

# 2. Детекторы -> JSON с флагами
node .claude/skills/kostya-ai/scripts/kostya-audit.mjs /tmp/rop.json > /tmp/kostya.json

# 3. Дайджест для Ивана / РОПа
node .claude/skills/kostya-ai/scripts/kostya-digest.mjs /tmp/kostya.json > /tmp/digest.md

# опции audit: --mgr "Имя"  --deal ID  --since YYYY-MM-DD  --today YYYY-MM-DD
# опции digest: --top N (сколько косяков на менеджера, default 5)  --format md|json
```

Скрипты на голом Node (без зависимостей). Сеть к `glassmemory.bitrix24.ru` из песочницы заблокирована - снимок всегда берётся из ветки данных, живой запрос идёт только в GitHub Actions.

## Пайплайн разбора (6 шагов)

**Шаг 1. Снимок.** Взять `rop.json`, проверить `generated_at`. Если снимку больше 36 часов - сказать об этом в шапке дайджеста, не молчать.

**Шаг 2. Детекторы.** `kostya-audit.mjs` гоняет 14 детекторов (полный каталог с признаками и порогами - `references/defect-catalog.md`). На выходе плоский список флагов: `{deal, mgr, code, severity, fact, should, evidence}`.

**Шаг 3. Проверка на ложное срабатывание.** Обязательный шаг, не пропускать. Три известных источника вранья в данных описаны в `references/data-contract.md`:
- `lastTouch` / `touch90` недостоверны (228 из 650 открытых сделок имели активность за неделю при нулевых касаниях). Никогда не выносить обвинение «менеджер не касался клиента» на одном этом поле.
- Поля «Дата решения клиента» и «Дата следующего контакта» в Bitrix24 ещё не созданы (ТЗ Кости не внедрено). Детекторы D05/D13 работают на прокси и помечены как прокси.
- Сделки без истории стадий (`hist: []`) - dwell не считается, сделка идёт в отдельную корзину «нет данных», а не в «всё хорошо».

**Шаг 4. Разметка Protocol 9.** Каждая цифра в дайджесте - `[ДАННЫЕ]` со ссылкой на поле снимка либо `[ГИПОТЕЗА]` с допущением. Пороги детекторов - гипотеза до калибровки (см. ниже).

**Шаг 5. «Как надо было».** По каждому косяку взять формулировку из `references/phrasebook.md`. Не сочинять свою: библиотека собрана из рекомендаций Кости дословно. Если ситуации в фразебуке нет - написать новую и добавить в файл, а не выдумывать разово.

**Шаг 6. Ранжирование.** Дневной индекс дисциплины по `references/scoring.md`, разбивка «молодец / норма / холодец». Минимальная выборка - 10 открытых сделок у менеджера, иначе в раздел «мало данных». Это прямое требование самого Кости: он сам оговорил, что выборка из 5 сделок «носит ограниченный характер».

## Формат дайджеста

```
# Разбор дня <дата>
Снимок Bitrix: <generated_at>, открытых сделок N

## Светофор
Молодец: <имена + индекс>
Норма:   <имена + индекс>
Холодец: <имена + индекс>
Мало данных: <имена>

## Топ-косяки дня (severity DESC)
### <Менеджер> - индекс X.X/10 (вчера Y.Y)
1. [D02 ТИШИНА] Сделка 96809 «...» - 46 дней без активности на стадии «КП отправлено»
   Как надо было: <фразебук>
   Действие до: <дата>
...

## Что стало лучше со вчера
## Системные дефекты (не вина менеджера)
## Данные, которых не хватает
```

Раздел «Что стало лучше» обязателен. Костя в каждом из 11 документов начинал с сильных сторон и требовал переводить эпизодические удачи в норму. Дайджест только из косяков менеджеры перестанут читать за неделю.

Раздел «Системные дефекты» тоже обязателен. Костя в каждом документе разделял проблему на индивидуальную и системную. Если «Дата решения клиента» не создана в Bitrix24 - это не косяк Лакомовой, это невнедрённое ТЗ, и вина РОПа/интегратора.

## Тон

Костин, не мой. Прямо, по фактам, без яда и без реверансов:

- **Факт, потом оценка.** «Сделка 229 дней на стадии "Принимают решение", стадия не менялась ни разу» - потом вывод. Не наоборот.
- **Оценивать действие, не человека.** «Не зафиксировала дату» вместо «безответственная».
- **Никаких "выглядит хорошо"** и «в целом неплохо». Либо норматив выполнен, либо нет.
- **Сильные стороны называть конкретно.** Не «хорошо общается», а «расчёт за 20 минут в сделках 4, 5, 6».
- **Никакого канцелярита.** Правила из `.claude/skills/humanizer-ru` применяются к дайджесту: em dash запрещён, «в ближайшее время» в тексте самого дайджеста - позор.

## Пороги: что данные, что гипотеза

Костя в ТЗ оставил тайминги пустыми (`Требует разбора в течение __ рабочих часов`) - осознанно, чтобы компания их определила. Дефолты в `kostya-audit.mjs` откалиброваны по снимку 2026-08-07 (650 открытых сделок) и помечены `[ГИПОТЕЗА - калибровка]`.

**Правило калибровки:** через 2 недели ежедневных прогонов сверить долю флагов с реальностью. Если детектор даёт больше 30% флагов по стадии, порог слишком жёсткий - это шум, а не сигнал. Костин же совет из ТЗ: «Запустить автоматизацию сначала с мягкими лимитами, через несколько недель отрегулировать».

Пороги правятся в одном месте: `STAGE_LIMITS` в `scripts/kostya-audit.mjs`. Не хардкодить их в тексте дайджеста.

## Ростер меняется - паттерны нет

Костя разбирал 8 менеджеров (6 GG + 3 GM). На снимке 2026-08-07 открытый пайплайн держат в основном другие люди: Юлия Шура-Бура (156 сделок), Татьяна Лакомова (119), Ольга Маслова (102), Юлия Лысанова (97), Алина Платонова (94). Безмащука и Белова в открытом пайплайне нет вообще.

**Следствие:** скилл работает по тому, кто в снимке сегодня, а не по Костиному списку. Профили из `references/manager-baselines.md` - исторический baseline на 2026-06-30, применять только к тем, кто в нём есть, и только как проверку на рецидив («Лакомова в июне бросала сделки после 1-2 касаний - воспроизводится ли это сейчас»). Для новых людей baseline набирается за первые 14 прогонов.

## Слой B: коммуникация (реализован)

Половина Костиных находок про **текст сообщений**: пустые письма, отсутствие имени, «в ближайшее время», «закрутился, забылся», орфография, защита вместо извинения. В `rop.json` тел сообщений нет, поэтому слой B работает на отдельном источнике: ручной выгрузке диалогов Bitrix24 (воронка C49, лист «Диалоги»).

```bash
# 1. xlsx -> jsonl
python3 .claude/skills/kostya-ai/scripts/dialogs-xlsx-to-jsonl.py выгрузка.xlsx /tmp/dialogs.jsonl
# 2. восстановить направление in/out
python3 .claude/skills/kostya-ai/scripts/dialogs-normalize.py /tmp/dialogs.jsonl /tmp/msgs.jsonl
# 3. метрики по менеджерам
python3 .claude/skills/kostya-ai/scripts/dialogs-analyze.py /tmp/msgs.jsonl /tmp/analysis.json
# 4. сайт разборов
python3 .claude/skills/kostya-ai/scripts/build-site.py /tmp/analysis.json /tmp/msgs.jsonl \
  analytics-mvp/public/kostya-managers.html /tmp/kostya.json
```

**Что даёт слой B, чего не даёт rop.json:** время ответа клиенту в рабочих минутах (медиана, p75, p90), диалоги, оборвавшиеся на сообщении клиента, доля обещаний с конкретным сроком, квалификация (бюджет, срок, ЛПР), возражения клиентов, эскалации к руководителю, дефекты текста.

**Ключевая особенность формата.** В выгрузке колонка «Кто написал» помечает менеджером почти всё (37008 из 37095 строк). Реальный автор зашит в текст комментария подписью Wazzup: `<иконка> Имя Фамилия: текст`. `dialogs-normalize.py` восстанавливает направление по трём сигналам: системная пометка «Отправлено» и «Принято», совпадение имени с ростером менеджеров, и отдельная корзина `unknown` для служебной подписи «Телефон» (2985 сообщений, обе стороны, надёжно не разделяются).

**Периодичность.** Выгрузка ручная, поэтому слой B прогоняется не ежедневно, а по мере получения новой выгрузки. Ежедневный дайджест (слой A) обязан писать, на какую дату актуален коммуникационный разбор.

Не делать вид, что проверено всё: звонки в выгрузке представлены только метаданными (193 записи без транскриптов), голосовой канал не разобран.

## Сайт разборов

**Артефакты сборки НЕ публикуются и не коммитятся.** Репозиторий публичный, внутри разборов лежат цитаты клиентской переписки, имена сотрудников и суммы сделок. Сборка локальная, раздача решением Ивана. Пути закрыты в `.gitignore`.

Два сборщика:
- `build-site.py` собирает сводку для РОПа и Ивана: светофор, детализация заказов, скрипты продаж, дожимы, лид-магниты.
- `build-pages.py` собирает **по одному самодостаточному файлу на менеджера** в `analytics-mvp/public/kostya/`. При статике без бэкенда это единственный способ не показать человеку данные коллег: их физически нет в файле. Порядок блоков задан ТЗ и не произволен, «не ваша зона» стоит выше личных претензий.

Скрипты и лид-магниты на сайте живут в самом `build-site.py` (константы `SALES_SCRIPTS`, `FOLLOWUPS`, `MAGNETS`), править там. Каждый скрипт привязан к цифре из нашей переписки, а не к абстрактной методике: это требование, а не пожелание.

## Gate перед отправкой людям

Дайджест по конкретным сотрудникам - чувствительный артефакт. Перед первой рассылкой и перед любой сменой методики оценки:

1. Прогнать через `phoenix-eval` (Step 12.5, порог 8.0/10).
2. Показать Ивану. Персональные оценки сотрудников - HITL по Protocol 6.
3. Регулярный ежедневный дайджест после апрува Ивана идёт без повторного гейта, если методика не менялась.

Никогда не выносить в дайджест вывод об увольнении или PIP. Это зона `sales-director` + решение Ивана.
