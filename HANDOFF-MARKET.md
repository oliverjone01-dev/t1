## 3. Плановые сборщики (GitHub Actions)

Единственный **плановый** сборщик Маркета - `ym-snapshots.yml`. Остальные ЯМ-воркфлоу запускаются вручную. Деплой сайта - общий `deploy-pages.yml`.

### 3.1 `.github/workflows/ym-snapshots.yml` - «Market snapshots (Яндекс Маркет, прямой)»

- **Крон:** `40 6 * * *` UTC (~09:40 МСК), после OZON (06:00) и Директа (06:20). `concurrency: ym-data` (не отменяет идущий), `timeout-minutes: 120`, Node 22, рабочая папка `analytics-mvp`, `npm ci`.
- **Ручной запуск** (Run workflow) с полями: `shows_days` (по умолчанию 7), `realization_months` (пусто = текущий + прошлый месяц; явно: `2026-04 2026-05`), `orders_refetch` (`yes` = полный пересбор заказов от пола), `orders_floor` (пусто = 2026-02-01, раньше пола заказы не тянутся вообще), `report_budget` (по умолчанию 10 отчётов за прогон), `dump_orders` (номера заказов через запятую, сырые строки в `_probe/orders_raw.json`).
- **Шаги по порядку** (npm-скрипты из `analytics-mvp/package.json`):
  1. маскировка ключей; нет ни одного ключа → стоп;
  2. md5-слепок OZON (`public/*.html`, `data/*`) и база накопительных файлов `data-ym` для дельта-гейта;
  3. `ym:orders` (заказы `stats/orders` по всем кампаниям, инкремент по дате создания + перетяжка хвоста 45 дней; **fail-closed**);
  4. `ym:catalog` (товары, цены, остатки; мягкий шаг);
  5. **промежуточный коммит** `data-ym` в ветку запуска (по расписанию `main`): «data-ym: заказы и каталог Маркета <дата> (промежуточный)»;
  6. отчёты Маркета, все мягкие, общий бюджет `YM_REPORT_BUDGET`: `ym:realization` (отчёт о реализации по месяцам и магазинам), `ym:netting` (реестр взаиморасчётов, «ledger»), `ym:services` (акт услуг), `ym:bonuses` (баллы), `ym:promo` (буст, полка, показы), `ym:shows` (показы и воронка по дням, `YM_SHOWS_DAYS`);
  7. `ym:derive` (производные в контракте OZON; **fail-closed**);
  8. **дельта-гейты:** `validate-snapshot.ts` (просадка 30-дневных витрин >40% = стоп) и `ym/validate-facts.ts` по каждому накопительному файлу (потеря собранного месяца = стоп; пороги `YM_FACTS_DROP_GATE` 0.1, `YM_FACTS_GROW_GATE` 0.25);
  9. `ym:join` (таксономия и себестоимость из `fixtures/`), `ym:reconcile` (сверка §15 → `reconcile.json`), `ym:build` + `ym:smoke` (страницы `/market/`);
  10. гейт «OZON байт-в-байт не изменился» (md5) и гейт «ключ не попал в HTML и данные» (grep);
  11. **финальный коммит** `data-ym` + `public/market`: «data-ym: снимки Яндекс Маркета <дата>», 5 попыток push с наложением своих файлов поверх уехавшего main; все попытки неудачны → прогон красный;
  12. `ym:ledger-fresh` - тревога после коммита: реестр кабинета отстаёт от вчера на 2+ дня → прогон красный → деплой не запускается.
- **Что пишет:** всё в `analytics-mvp/data-ym/` (§4) и `analytics-mvp/public/market/`. Коммиты без `[skip ci]`, поэтому push в main запускает `analytics-tests.yml` и `deploy-pages.yml`.
- **Лимиты Маркета** (проверено прогонами, `YM_MARKET.md`): отчёты `goods-realization` и `united-netting` - 1 генерация в 2 минуты на кабинет; `shows-sales` - 1 в 6 минут (HTTP 420); окно `stats/orders` не больше 30 дней. Поэтому один прогон добирает 3-10 пар «месяц/магазин», остальное помечается `pending` в `realization_state.json` и добирается следующими прогонами без флагов.
- **Телеграм-уведомлений нет.** Сигнал о проблеме - красный прогон в Actions и полоса «Сверка §15» на страницах.

### 3.2 `.github/workflows/deploy-pages.yml` - «Deploy to GitHub Pages»

- Триггеры: push в `main` по `analytics-mvp/**`; `workflow_run` после успешного «Market snapshots…» (и OZON, Direct, GEO); страховочный крон `47 9 * * *`; ручной.
- Шаг «Build MARKET dashboard (/market/)» (`continue-on-error: true`): если `data-ym/history.ndjson` или `skus_live_30d.json` пусты - раздел пропускается; иначе `ym:derive` → `build-site.ts` → `build-katya.ts` → `smoke.ts` с `DATA_DIR=data-ym OUT_DIR=/tmp/market-site PLATFORM=ym` → копия в `_site/market/`. **Деплой пересобирает страницы сам из `data-ym`, закоммиченный `public/market` для сайта не используется** (он нужен для просмотра в git и гейтов).
- Один Pages-сайт на весь репозиторий: OZON в корне `https://oliverjone01-dev.github.io/t1/`, Маркет в `/t1/market/`, хаб всех дашбордов `/t1/dashboards/`.

### 3.3 `.github/workflows/ym-ping.yml` - «Market ping (Этап 0, только чтение)»
Ручной. Список кампаний обоих ключей и пробный `stats/orders` за 7 дней. Ничего не пишет. Используется для проверки ключей (§1 п.4).

### 3.4 `.github/workflows/ym-boost-probe.yml` - «Probe отчётов Маркета по продвижению»
Ручной (и по push своих файлов). Разовая разведка отчётов `boost-consolidated`, `shows-boost`, `shelf-statistics` за период. Ничего не коммитит. Та же группа `ym-data` (общий лимит генерации).

### 3.5 `.github/workflows/analytics-tests.yml` - «Тесты аналитики (vitest + smoke обеих площадок)»
На PR и push в `main` по `analytics-mvp/**`: `npm test`, сборка OZON и Маркета во временную папку, smoke. Секретов не требует. Падает, если `data-ym` пуст. Открытый хвост N2: добавить `.github/workflows/ym-snapshots.yml` в `paths`.

### 3.6 Если плановый прогон красный - где смотреть
- Шаг «ym:orders» красный: ключ, сеть Маркета или нет кампаний. Прогнать «Market ping».
- Красный дельта-гейт: см. вывод `validate-facts` в логе, какой файл и месяц просел. Это защита от тихой потери данных (реестр ошибок E027, E076, E082). Если добирается новый инструмент или месяц, гейт может сработать ложно: разобраться по логу, не ослаблять пороги без записи в `knowledge/decisions.md`.
- Красный «ledger-fresh» при зелёных данных: Маркет ещё не выложил реестр за позавчера. Обычно само проходит на следующий день; если 3+ дня - писать Ивану.
- Красный push: main уехал, 5 попыток не хватило. Перезапустить воркфлоу вручную без параметров.
- Параллельный ручной и плановый прогоны: промежуточный коммит ручного может откатить поле `at` в `realization_state.json`. Данные целы, смотреть содержимое (§9).

- E044: снимки данных коммитит только бот в `main`; рабочие ветки без данных.
- Мерж в main - только по слову Ивана; починка main - отдельная ветка и squash-мерж, после squash ветку пересоздать от main (E045).
- Кабинет Маркета руками не трогать; мутаций через API нет по построению (v22: «пока ничего не делаем, только разбираемся»).
- Цену на Маркете вниз не трогать: она влияет на индекс цен OZON (Иван 16.10).

**Деньги и метрики**
- L78/L79: граница реестра по кабинету; реестр отстаёт на 2+ дня - тревога `ledger-fresh` красит прогон; `ym:netting` остаётся мягким.
- L80: конец периода «Отчета» и блока ACC = последний день, за который пришли сборы по заказам.
- L81: проводки «не будет переведён / удержан из-за отмены» - не продажа и не возврат, справка «оплачено и отменено» (PAYMENT_STATUS).
- L82: два столбца «Начислено»: (1) как начислил Маркет, справочно; (2) основа - заказы с проведённым сбором за продажу, весь платёж в день сбора; от (2) считаются К выплате, С/С, наша доставка, АДМ 30%, налог 15%, чистая.
- L85: перевозка заказов, отменённых Маркетом без продажи, входит в «Нашу доставку» в день отмены.
- L87: блок 5 «Отчета»: буст продаж, буст показов, полки - расход, выручка, ДРР; спека `ym-promo-block5.yaml`.
- Баллы идут справочно, в «Начислено» не входят (28.09); «Списал» - только деньги, баллы в блоке 4; «Перевёл» - по месяцу проводки; блок движения денег седьмой, все строки из реестра `netting.ndjson` (v17-v18).
- Расход на рекламу = деньги + баллы; ДРР от всей доставленной выручки по цене карточки (так считает и Маркет); заказы = товарные строки без услуг; ставка буста = буст / (цена × кол-во) (v19-v20).
- Для свода «Деньги» ставки по `knowledge/semantic/ym-rates-adm-tax.md` (АДМ от «Поступления», налог от «Оплатил клиент»); для «Отчета» и прототипа ставки - АДМ 30% от «К выплате», налог 15% от «Начислено». Разные экраны, не путать (v25).
- Механика буста: списанная цена ≠ выставленная ставка; про действия сотрудника писать только доказанное - подъём потолка (E091). Вывод «аукцион второй цены» снят ФЕНИКСОМ. «Скидка за лояльность / Возврат списания» = возврат размещения при возврате товара, не буста (v22). Пилот снижения ставки (П5) не запускать без П9 и П4 (v20).
- Зеркала: «Полка», «Буст за показы», «Баннеры» Маркет удерживает в следующем месяце из «Внесено продавцом»; мебель - в том же месяце (v18).

**Сверка с 1С (L92, v26)**
- ДБС-магазины проводятся «Отчётом комиссионера» по отчёту Маркета о реализации (нетто = доставлено − возвраты); ФБС-магазин FBS OOO - реализациями «Яндекс маркет фбс» по «доставлено» gross; возвраты ФБС - отдельными документами «Возврат товаров от покупателя».
- Пара документу 1С ищется по отчёту Маркета о реализации, не по выгрузке заказов (E092: иначе ложные 1,7 млн).
- «Сошлось» только между семьями источников: банк 1С / документы 1С / реестр API / файл кабинета. Файл кабинета = API до рубля (проверено на 9 парах 20.10).
- Три разных месяца у одного заказа: отчёт об исполнении поручения - по дате оплаты, отчёт о реализации и 1С - по доставке, выгрузка заказов дашборда - по дате сбора за продажу. Сравнивать только одноимённые базы.

## 9. Грабли (в силе)

- Работу по хендоффу начинать с `git fetch origin <ветка>` и проверки открытых и смерженных PR (E059).
- Классификатор auto-режима не даёт `git reset --hard`, `git pull`, `merge --ff-only` после пересоздания ветки: обход `git branch -m` старой + `git checkout -b <ветка> origin/<ветка>`.
- Писать абсолютные пути: рабочая папка Bash сбрасывается между вызовами.
- `orders.ndjson`: строки «Доставка» с тем же sku и `service: true` - фильтровать, иначе ставка 300%. API заказов делит платёж за доставку между позициями: сверять по всем позициям заказа.
- `sku_views`: строк на SKU-день несколько, суммировать; первая строка 06.09 - агрегат за неделю.
- Удержания в реестре с минусом; проводки без статуса и «Справочно» - не деньги.
- Выгрузка заказов зеркал неполная до июля (кампания 21985942 без API).
- Дельта-гейт может ложно остановить прогон при доборе нового инструмента или месяца (E076, E082): смотреть лог, не ослаблять пороги молча.
- Слепок гейта «OZON байт-в-байт» после `reset --hard` давал ложную остановку (E088) - починено, но при правке воркфлоу помнить.
- Параллельный плановый и ручной прогоны: `at` в `realization_state.json` может откатиться, данные целы.
- Тесты на живом снимке не прибивать к числам и окну на дату написания (E083): окно выбирать из данных, лаг Маркета 1-3 дня исключать узко.
- Номер новой записи в `knowledge/errors/registry.jsonl` брать по `origin/main`, не по ветке (E089).
- В markdown-таблицах скриптов разделитель `---|---`; парсер по `" | "` рвёт таблицу.
- Лимиты API проверять пробой до кода (E018): период, страница, rate, код лимита, параллельность.
