**Стадий, которые Костя просил создать, в Bitrix24 нет:**
- «Счёт отправлен» между «Принимают решение» и «Предоплата получена». Без неё контроль оплаты счёта не отделён от ожидания решения.
- «Связаться позже» (или «Отложено»). Без неё зависшие сделки некуда девать, и они копятся на активных стадиях. Это прямая причина того, что на «КП отправлено» лежат 207 сделок с медианой 31 день.

## Бизнес-логика по стадиям (по Косте)

**Новая сделка.** Первичный звонок или сообщение в первые часы. Костя: «очень важно быстро прорабатывать тёплые заявки, чтобы конкуренты не оказались быстрее».

**Расчёт / Квалификация.** Транзитная стадия. Потребности выявлены, идёт техническая проработка. Минимум времени.

**Формирование ТЗ.** Совместная проработка с конструкторским отделом. Без движения дольше 3 дней эскалация РОПу.

**КП отправлено.** Ключевая стадия и главная свалка воронки. Костин канон: стадия только для ожидания обратной связи по **готовому** предложению. Любые доработки и согласования это возврат на «Формирование ТЗ». Обсуждение доставки на этой стадии (реальный случай из части 1) означает, что стадия давно не соответствует реальности.

Роботы по ТЗ: через 1 рабочий день задача менеджеру «уточните результат», через 3 рабочих дня задача менеджеру и РОПу.

**Принимают решение.** Правило «нет даты, нет стадии». Стадия применяется только когда клиент назвал конкретную дату ответа (1-7 дней). Не для обсуждений, не для доработок, не для ожидания оплаты, не для размышлений «на потом».

Роботы по ТЗ: обязательное поле «Дата решения клиента» с блокировкой перехода без него; в указанную дату задача менеджеру «получить финальное решение»; через день после даты без движения эскалация РОПу.

Три исхода в дату решения, третьего не дано: согласен → «Счёт отправлен», отказ → закрыть с причиной, перенос → обновить дату или увести в «Связаться позже».

**Долгострой.** Стадии не было у Кости, появилась в Bitrix24. По смыслу это флаг производственной задержки. Риск: превращается в свалку. На 2026-08-07 там 103 сделки, из них 42 без активности дольше 30 дней.

**Предоплата получена.** Финальная подготовка к передаче в производство. Дементьев: сделка застряла тут после предоплаты, следующих шагов не видно, это операционный риск. Детектор D08 ловит случай, когда карточка производства уже заведена, а сделка всё ещё здесь.

**Производственные стадии.** Не зона продаж, кроме SLA и информирования клиента. Робот по ТЗ: задача менеджеру за 2 дня до плановой даты готовности.

## Совет Кости по внедрению, не пропускать

Из ТЗ, раздел «Общие советы»:

1. **Неделя чистоты перед автоматизацией.** Руками разобрать текущие зависшие сделки, прежде чем включать роботов. Иначе роботы завалят отдел задачами по мёртвым сделкам, и менеджеры научатся игнорировать задачи.
2. **Мягкие лимиты сначала.** Запускать не с 1 дня, а с 2, через несколько недель отрегулировать по реальной скорости компании.
3. **Контроль через задачи, а не через сделки.** Просроченная задача явный индикатор проблемы. Это и есть основной инструмент РОПа.
4. **Единые правила игры.** Встреча, на которой утверждается, что считается зависанием, как заполнять дату решения, когда переносить в «Связаться позже». Зафиксировать в Регламенте.
