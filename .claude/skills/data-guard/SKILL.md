# data-guard: цифры без переделок

Скилл собран из 337 реальных переделок в 9 чатах аналитики (июнь-сентябрь 2026) и внешнего исследования практик (dbt, Great Expectations, semantic layer, документация Ozon, Маркета, WB, Bitrix24, Директа). Каждый шаг закрывает класс ошибок, который уже стоил переделок. Классы К1-К14 описаны в `references/classes.md`.

Главный принцип: **заказчик не должен работать контролем качества.** Всё, что он поймал бы правкой, ловим до сдачи.

## Когда шаги можно сокращать

- Разовый вопрос «сколько было X за период» без кода: шаги 1, 5, 6.
- Правка вёрстки без изменения чисел: шаг 6 и хуки.
- Всё, что меняет формулу, источник, период, фильтр или сборщик: все 8 шагов.

## Шаг 1. Pre-mortem (до кода, 5 минут)

1. Определи тип задачи: деньги маркетплейса / CRM-воронка / реклама / эксперимент / сборщик-API / прочие цифры.
2. Запусти `python3 .claude/skills/data-guard/scripts/registry_match.py "<описание задачи>"`. Он вернёт топ прошлых ошибок из `knowledge/errors/registry.jsonl` для этой задачи. Вне репо t1 используй `references/classes.md`.
3. Открой раздел своего типа в `references/premortem.md`: там риски и готовые вопросы заказчику.
4. Выдай заказчику одним сообщением: **5-8 рисков** с номером класса и **3-5 вопросов**, ответ на которые меняет код. На каждый вопрос дай свой вариант с пометкой (рекомендую), чтобы можно было ответить «да».
5. Не начинай код, пока нет ответов на вопросы, влияющие на формулу. Остальное делай параллельно.

## Шаг 2. Спека метрики (подпись до кода)

Для каждой новой или меняемой метрики заполни `templates/metric-spec.yaml` (поля и зачем они: `references/metric-spec.md`). Файл кладётся в `knowledge/semantic/metrics/<id>.yaml`.

**Шесть полей блокирующие.** Без подтверждения заказчика по ним код не пишется:
- отношения: числитель и знаменатель из одной популяции и по одной дате;
- отмены и возвраты: gross или net, к какой дате относятся;
- дата привязки (создание / оплата / отгрузка / доставка / начисление);
- период или когорта, окно конверсии;
- часовой пояс и границы: `[с, по)`, Europe/Moscow, неполный день помечается;
- эталон: 3-5 реальных строк, посчитанных вручную и подтверждённых. Они становятся тестом.

Смена любого из шести полей = новая версия спеки с новой подписью, а не правка на ходу.

## Шаг 3. Probe источника (до кода)

Новый эндпоинт, поле CRM, отчёт или выгрузка: пройди 12 пунктов `references/api-gotchas.md` §Probe и сохрани короткий итог в `knowledge/semantic/probes/<source>.md`. Минимум:
- найти в ответе 3 известные сущности из кабинета (заказ, возврат, услугу);
- максимальный период, страница, rate-limit и **код** лимита (Маркет отдаёт 420, не 429);
- какая дата у фильтра и в какой TZ;
- копейки или рубли, знак списаний, коды EN или RU;
- чем отличаются «пусто», `[]`, 204, `NO_DATA` и 0.

Перед кодом сверься с таблицей известных подвохов в `references/api-gotchas.md` (Ozon, Маркет, WB, Bitrix24, Директ, Метрика).

## Шаг 4. Код со встроенными проверками

Инварианты из `references/invariants.md` вызываются в билдере **до записи результата** и роняют сборку. Готовые функции: `scripts/invariants.py`, `scripts/invariants.ts`.
- ключ сущности уникален и не пустой; дедуп только по объявленному полному ключу;
- доля от 0 до 1, `num <= den`;
- сумма частей = итог (допуск 0.01);
- пропуск = `null`, не 0; `|| 0` на входе метрики запрещён;
- у снимка есть `loaded_at`, устаревший снимок роняет сборку;
- запись только в явное окно `[start, end]`, данные вне окна не меняются;
- сегодняшний день помечен `partial`;
- одна функция на одну логику (поиск с/с, нормализация SKU, база дат) в общем модуле, копии запрещены;
- правка только в билдере или шаблоне, не в сгенерированном HTML;
- тесты с инъекцией `now`, не на литералах дат.

## Шаг 5. Сверка с независимым источником

Семейства источников: **банк** / **документы** (УПД, отчёт о реализации, акт, ведомость, свод заказчика, 1С) / **API** / **кабинет**. API и кабинет считаются одним семейством.

- Сверяй только между разными семействами. Сверка файла с самим собой или API с кабинетом ничего не доказывает.
- Допуск до копейки внутри документа. Любой остаток объясняется списком строк.
- Расхождение «месяц заказа против месяца начисления» раскладывай таблицей сдвига дат, а не называй ошибкой данных.
- Три типа периода: закрытый месяц, часть месяца, текущий месяц (`knowledge/os/analytics-dod.md`).
- Покрытие: доля SKU и оборота с данными, непокрытое подсвечено на странице.

## Шаг 6. Заявление «готово» только с доказательством

Таблица «утверждение -> доказательство» в `references/evidence.md`. Коротко:
- «сошлось / сверено / совпадает» = две цифры, два источника разных семейств, разница и её причина;
- «API не отдаёт / данных нет» = запрос, ответ, дата проверки;
- «исправлено» = тест, который падал до правки и проходит после;
- вывод на выборке = n рядом с процентом, окно выбрано до просмотра данных (`references/stats.md`).

Слова «точно», «никогда», «всегда», «нет намеренно» без пробы запрещены. Если доказательства нет, пиши «не проверено» и что нужно для проверки.

## Шаг 7. ФЕНИКС, затем слияние

Изменение чисел в дашборде = критический артефакт. Step 12.5 до слияния, после `return` повторный аудит. Слияние без `go` только по записанному решению Ивана. Хук `data-guard` на слияние спросит подтверждение и попросит причину.

## Шаг 8. Ретро и реестр (в конце задачи)

1. Посчитай долю переделок: `python3 .claude/skills/data-guard/scripts/rework_rate.py --branch <ветка>`.
2. Каждая правка заказчика или откат, которые ты признал своим недосмотром, = запись в `knowledge/errors/registry.jsonl` (формат и правила: `references/retro.md`). Совпадает с существующей записью: увеличь `count`, обнови `last_seen`.
3. Лестница: 1 случай = запись; `count >= 2` = пункт в чеклисте этого скилла; `count >= 3` или класс К11/К13 = хук.
4. Реестр и хендофф уходят в main отдельным коротким PR.

## Git и автоматика

Правила для снимков, веток, трейсов и cron: `references/git-hygiene.md`. Главное: снимки коммитит только бот и только в main; после squash ветка пересоздаётся от `origin/main`; пересборка на main запрещена; трейсы пачкой.

## Хуки data-guard (в репо t1)

Все хуки предупреждают, ничего не блокируют. Переопределить можно маркером `DG_OVERRIDE="причина"` в команде. Причина пишется в `traces/<дата>/data-guard.jsonl`.

| Когда | Что делает |
|---|---|
| Старт сессии | короткая памятка К1-К14 |
| Сообщение с цифрами | напоминает про скилл и 3 похожие прошлые ошибки |
| Слияние PR / push в main | нет `go` ФЕНИКСА после последнего коммита: спросит подтверждение |
| Сборка на main | спросит подтверждение |
| Коммит только трейсов или снимков из рабочей ветки | предупредит |
| Правка сгенерированного HTML | предупредит, где билдер |
| «Сошлось» без двух цифр | попросит доказательство |
| Конец задачи с фиксами | напомнит про ретро |
